## 📖 비전공자 친화 — 무엇을 왜 하는가

### 비유 — "내 컴퓨터 → 24시간 데이터센터"

**현재 상태**: 사용자 Windows 11 컴퓨터에서 worker (데이터 일꾼) 가 돌아갑니다 — Binance 실시간 시세를 Supabase DB 에 매초 적재. 하지만:

1. **컴퓨터 끄면 DB 멈춤** — 이미 본 사고: 사용자가 Wi-Fi 끊고 컴퓨터 끄자 worker 정지 → DB 40시간 stale → 사용자가 카드 갱신 안 됨 발견.
2. **Windows 환경 특수 사고** — USDM `fstream.binance.com` 만 selective stuck (메시지 0건). SPOT/COINM 같은 클래스로 정상. backend-infra-specialist 진단 결과 "Windows + 사용자 ISP + ws library + 큰 페이로드 콤보" 강한 의심. M1.6 Step 4 hotfix B (mini 6필드 + REST 1분 폴링) 로 USDM 1분 stale 까지 후퇴 보강.

**Hetzner 이전 후 자연 해결 가능성**:
- **Linux TCP stack** 이 Windows 와 다름 — payload-size selective failure 회피 가능성 매우 높음
- **데이터센터 IP** 가 사용자 ISP 와 다름 — fstream selective stuck 자연 해소 가능성
- **24/7 가동** — 컴퓨터 종료 의존성 0

### 베타 배포 전이지만 지금 이전하는 이유

사용자가 베타 배포 자체는 늦게 진행하지만, **개발 중 사용자 검증이 USDM 1분 stale + fstream stuck 으로 자꾸 노이즈** 발생. M1.6 Step 5 (CI RLS + orchestrateOnce 단위 테스트) + M1.6 Step 6 (E2E + M1 완료 선언) 검증 자체가 worker 데이터 stale 영향 받음. **안정된 환경에서 Step 5/6 진행 = 검증 신뢰도 ↑**.

## 🧭 주요 의사결정

### 1. **Plan = CPX21 €11.99/월** (사용자 확정 2026-04-29)

100명 이하 가성비 조건. backend-infra-specialist 분석 — TRAVIS worker 부하의 99% 가 Binance WS + Supabase upsert (사용자 수 비례 X). CCX13 dedicated 의 €4/월 (€48/년) 차이는 베타 100명 이상 도달 후 실측 트리거 발동 시 승급이 합리적.

### 2. **위치 = Falkenstein DE** (사용자 확정 2026-04-29)

해외 사용자 타겟 + EU 데이터센터 가 글로벌 평균 latency 최저 + 20TB 트래픽 무료 (글로벌 분산 트래픽 비용 안전). Hillsboro OR 차순위는 Binance us-west PoP latency 우위지만, Supabase Cloud 로의 매초 upsert 워크로드에서 EU 가 미세 우위.

### 3. **Backup ON** (사용자 확정 2026-04-29)

월 +€2.40 안전망. worker.env 분실 / disk 오류 / Hetzner 자체 사고 대비. 베타 직전 안전망 가치 > 비용.

### 4. **OS = Ubuntu 24.04 LTS** (Claude 권고)

2026 시점 최신 LTS. Node 22 LTS / pnpm 9 / systemd / fail2ban / unattended-upgrades 모두 안정 지원. 22.04 도 가능하지만 5년 주기 LTS 정공.

### 5. **6 substeps 순차 + 사용자 컨펌 모드** (사용자 확정 Q6=A)

각 substep 완료 시 사용자 컨펌 → 다음 진행. 첫 Hetzner 배포 안전 모드. 잘못 굳어진 설정 되돌리는 비용 회피.

### 6. **GitHub Deploy Key vs PAT** — Substep 0.3 시점 결정

사설 repo 인 경우 Deploy Key 가 보안 우수 (repo 한정 read 권한). 사용자 첫 사용이라 절차 가이드 후 결정.

### 7. **`/etc/travis/worker.env` 권한 0640 root:travis** (backend-infra-specialist 권고)

systemd `Environment=` 직접 입력은 비추 — journald 로그에 secret 노출 위험. EnvironmentFile 분리 + root 소유 + travis 그룹만 read.

- **Hetzner Backup vs Snapshot 차이**: Backup 은 자동 (7일 7개) — 본 Step 채택. Snapshot 은 수동 (보관 무제한, €0.011/GB/월) — 큰 변경 직전 추가 안전망용 권장.
- **`fstream.binance.com` selective stuck 재발 시**: Hetzner 에서도 재발하면 Binance API key 또는 ASN 기반 차단 가능성. 별도 진단 — backend-infra-specialist 자문 + crypto-domain-expert 자문 동시.
- **베타 배포 시점 alignment**: 사용자가 베타 배포할 때 Vercel `apps/web` 의 Supabase URL 변경은 **불필요** — Hetzner worker 도 같은 Supabase 인스턴스 쓰므로 자동 일치. 단 Hetzner worker 의 `BINANCE_API_KEY` 가 사용자 베타 배포 시점에 갱신 필요할 수 있음 (M1.7 Step 1 allowlist 와 무관).

### 3단계. bootstrap.sh 다운로드 + 실행 (사용자 + Claude 협업)

> **이 단계는 Claude 가 새 세션에서 `apps/worker/deploy/hetzner-bootstrap.sh` 를 작성하면, 사용자가 GitHub Raw URL 또는 scp 로 서버에 옮겨 1회 실행**.

기본 실행 흐름 (Claude 가 새 세션에서 정확한 명령어 다시 안내):
```bash
# Hetzner 서버에서 (root 접속 상태)
```

`bootstrap.sh` 가 자동 처리할 작업:
- `apt update && apt upgrade -y` (시스템 최신화)
- `apt install -y ufw fail2ban unattended-upgrades` (방화벽 + brute-force 방어 + 자동 보안 패치)
- `ufw default deny incoming + allow 22/tcp + ufw enable` (외부 incoming 22번만 허용)
- non-root user `travis` 생성 + sudoers 등록 + `~/.ssh/authorized_keys` 복사
- `systemctl enable --now fail2ban` (sshd jail 자동 적용)
