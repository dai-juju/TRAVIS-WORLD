## Sub-step 2-A — 기반 배관 (freshness 조회 + 증분 startMs 주입) ✅ 2026-06-04

### 무엇을 / 왜
forward-fill의 본질 = **"어디까지 채웠나(freshness) → 그 다음 봉부터(증분 startMs) → 채우기"**. 그 가장 아래 벽돌 2개를 깐다. 나머지 sub-step 전부가 이 둘에 의존.

1. **`getMaxRecordedAt` 신규 dataService 메서드** — "이미 어디까지 채웠나"의 절대 진행점. 기존 `countHistoryFuturesIndicatorSince`(row 수)는 증분에 부적합(진행점 없음) → MAX 정공 (`[8-25]` (b) freshness 정밀화 토대).

## Sub-step 2-B — USDM forward-fill 본구현 (STUB 제거) ✅ 2026-06-04 (코드 완성)

### 무엇을 / 왜
`forwardFillTask.ts`의 STUB(로그만)를 실 로직으로 교체. M1.8.5가 채운 history가 05-31에 정지한 문제(`[8-26]`)를, DB 최신 봉부터 증분 수집해 미래로 계속 자라게 한다.

### 핵심 설계 — interval당 1회 호출 + 그룹별 스케줄
1. **코어는 `startMsOverride` 하나를 모든 interval에 적용** → 그러나 interval마다 freshness anchor가 다름(5m→05-31 12:05 / 1d→05-31 00:00). → forward-fill이 **interval마다 자기 anchor로 startMs를 계산해 `executeHistoryBackfill({intervals:[interval], startMsOverride})`를 1회씩** 호출. 코어엔 `intervals?` 부분집합 옵션만 추가(순수성 유지).
2. **interval 그룹별 별도 PollTask 3개** (§5 lock-in): 단기(5m/15m/30m) ~10분 / 중기(1h/2h/4h/6h) ~1h / 장기(12h/1d) ~12h. 단기봉은 5분마다 새 봉이 나오지만 1d를 같은 주기로 재조회하면 IP quota 낭비 → 그룹 분리가 최적화가 아니라 **quota 보호**.
3. **freshness → startMs 순수 함수 분리** (`forwardFillWindow.ts`): `computeForwardFillStartMs(anchorMs, intervalMs, nowMs, defaultLookbackMs)`. anchor 있으면 `anchor - 2봉`(마지막 2봉 재수집, 멱등), 없으면 `now - 14일` 폴백, now 초과 시 clamp. 네트워크 의존 0 → worker vitest로 단위 검증.
4. **graceful**: interval별 try/catch — 한 interval 실패가 다음·전체 task를 안 죽임(executeHistoryBackfill은 symbols 조회 실패 시 throw 가능 → 흡수). crash 금지(CLAUDE.md).
5. **IP quota 방어 위치**: forward-fill이 코어를 9번 호출해도 모든 fetch는 `client.ts`의 **모듈 전역 rate-limit 싱글톤**을 통과 → 1000 req/5min 한도는 한 곳에서 일괄 backoff. 호출 분리가 안전한 이유.
