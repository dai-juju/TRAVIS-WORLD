## 3. 핵심 설계

### 3.1 페이지 윈도잉 (backfillOneMetric)

- `startTime=cursor, endTime=endMs, limit=500` 으로 시간 오름차순 페이지 수신.
- cursor 전진 = 페이지 최대 recorded_at + intervalMs.
- **종료 조건 4중** (code-reviewer C1 반영): empty-page / cursor 전진 정체(`next ≤ cursor`) / `cursor ≥ endMs` / maxPages 상한. **`data.length < 500` 을 마지막 페이지로 단정 금지** (sparse/신규 상장 누락 방지).

### 3.2 per-page upsert (mixed-batch 안전)

- 페이지(≤500행)=한 metric=동일 key 집합 → `defaultToNull:false` ON CONFLICT 자연키 머지.
- `retryOnTransient` 래핑 (backend rec 3): 1회성 backfill 이라 done 후 페이지 유실 = 영구 결손. ON CONFLICT 멱등이라 재시도 안전.

### 3.3 state machine + freshness skip (fire-and-forget)

- idle→running→done. running 중 중복 진입 차단(+TierPoller inFlight). 예외 시 idle 복귀 → 다음 tick 멱등 재시도.
- freshness skip: 14일치 ≥ 20M row 면 재실행 차단. **잠정(code-reviewer C2)**: row-count 임계는 partial-run 오판 가능 → Step 5 per-interval 검증이 안전망, 배포 전략(D-Q5) 확정 시 completion-marker 로 대체 예정.

### 3.4 rate limit (100 req/min)

- 400ms→600ms throttle. crypto-domain-expert 권고 보수값(D-Q1 150 도 안전하나 IP 공유 margin).

## 8.7 windowing hotfix² — sampling 엔드포인트 dense 강제 (2026-05-31, 로컬 run 중 발견)

로컬 backfill 실행 중 DB 검증에서 발견: 5m 98심볼 시점 **6 metric 중 5개(OI/Top-LSR×2/Global/Taker)가 심볼당 ~500행**, basis 만 ~3,860행(정상 dense).

**원인**: Binance `/futures/data/*` 의 stat 엔드포인트(openInterestHist/LSR 3종/taker)는 `[startTime, endTime]` 범위가 limit 보다 넓으면 그 범위에 걸쳐 **~500개를 sampling** 반환. backfillOneMetric 이 매 페이지 `endTime=endMs`(14일 전체) 로 줘서 1페이지에 14일을 sampling → 심볼당 ~500행. basis 만 우연히 dense first-N 반환이라 정상이었음.

**수정**: 각 페이지 `endTime = min(cursor + PAGE_LIMIT × intervalMs, endMs)` (= 정확히 500 point 폭) 로 윈도우 고정 → 모든 엔드포인트 dense 반환. cursor 윈도우 단위 단순 전진 → code-reviewer C1("마지막 페이지 추정") 자연 해소. `historyBackfillCore.ts` backfillOneMetric. type-check + lint + 77 test PASS.

**영향**: 분량이 의도대로 복귀 — 5m 5 metric 이 ~500 → ~4032행/심볼. 총 요청 ~72,960 REST (원 계획치). ON CONFLICT 라 기존 sparse 행 위에 dense 재실행 = 빠진 point 추가 머지(삭제 불요). 로컬 재실행 필요.

## 9. history forward-fill 설계 논의 (2026-05-31, 사용자 질문 계기) → `[8-26]`

backfill 실행 중 사용자 질문: **"어차피 N분 주기로 폴링하는데, 그때 history 에도 같이 채우면 안 되나? 현재 방식이 뭐고 왜 이렇게 하나? 앞으로는 어떻게 채워지나?"**

### 9.1 현재 방식 (now vs history)

| 데이터 | 채움 방식 | 성격 |
|---|---|---|
| `now_*` | 실시간 WS + N분 폴링 → **덮어쓰기** | "지금 값" 1개. 과거 안 남음 |
| `history_*` | 거래소 history API **backfill** (9 interval 격자) | 시점별 9봉 시계열 |

본 Step 4 = history 를 **과거 14일치로 1회 backfill**.

### 9.2 왜 "실시간 append" 만으로 안 되나 (핵심)

1. **과거 복구 불가**: 실시간/폴링 append 는 "지금→미래"만 채움. 폴링 시작(며칠 전) **이전** 데이터는 DB 에 없음 → 거래소 history API backfill 이 **과거를 가져오는 유일한 경로**.
2. **봉 격자 정렬**: history 는 5m/15m/…/1d 정각 격자 필요. ~18분 불규칙 폴링은 격자 불일치. 거래소 history 는 이미 격자 정제값 제공.
3. **9봉 동시 생성 불가**: now 는 현재값 1개, history 는 같은 순간을 9 interval 로 분리 보관. 1폴링으로 9봉 못 만듦 (거래소가 봉별 집계).
4. **품질**: 거래소 history = 마감·집계 공식값. 폴링 스냅샷 = 찰나값.

### 9.3 앞으로(forward-fill) — 현재 미설계 (정직)

⚠️ backfill 완료 후 worker task 는 멈춤(dryRun:true / done) → **새 봉 자동 추가 안 됨**. history 는 backfill 시점 기준 14일 스냅샷으로 정지. 이를 자라게 하는 forward-fill 은 **M2 숙제** (`[8-26]`):
- **(A) 주기적 증분 backfill** (정공): 최근 1~2봉만 재조회. 단 same-IP ban → 별도 IP/worker(`[8-20]`) 전제.
- **(B) 실시간 append** (사용자 아이디어): 폴링값 격자 정렬 write. 5m 가능 / 장기봉은 봉마감 집계 필요.
- **(C) 혼합**: 단기봉 (B) + 장기봉 (A).

**M2 실사용 1주 후 결정** (deferred-decision 원칙 — 갱신 빈도/별도 IP 필요성 데이터 확보 후). 오늘 겪은 same-IP ban 이 (A)의 별도 IP 전제(`[8-20]`)를 실증.

> sliding window(`[8-18]`/D26) = "14일 초과분 삭제"(청소)로 forward-fill(추가)과 별개.
