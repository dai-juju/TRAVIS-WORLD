## 📖 비전공자 친화 설명

Step 3에서 "본채(사용자가 보는 웹 화면) 골조 + 인테리어"를 끝냈다면, **Step 4는 뒷마당에 작은 별채(데이터 수집 공장) 토대 + 전기 콘센트 매립**입니다. 별채(`apps/worker`)는 사람이 사는 곳이 아니라 **기계(데이터 수집 워커)가 살 곳** — 나중에 M1.3에서 Hetzner라는 임대 서버에 배포해서 24시간 돌면서 거래소(Binance 등)에서 가격·거래량을 긁어올 일꾼입니다. 지금은 텅 비어 있고 "안녕(`hello from travis-worker`)" 한 마디만 외치고 자연 종료합니다.

본채와 같은 자재(TypeScript, ESLint, Prettier)를 쓰지만 **3가지 핵심 차이**가 있어요. 첫째, **런타임이 다름** — 본채는 브라우저 + Next.js 번들러 환경, 별채는 Node.js만 (그래서 `tsconfig`의 `module`을 `bundler`가 아닌 `NodeNext`로 잡았고, 이게 `import "./supabase.js"`처럼 상대 import에 `.js` 확장자를 강제하는 효과를 냅니다). 둘째, **권한이 다름** — 본채는 누구나 가져도 RLS 보안 정책으로 막아주는 약한 키(`anon key`)지만, 별채는 모든 RLS를 무시하는 마스터키(`service_role key`)를 씁니다. 그래서 환경변수 이름에 절대 `NEXT_PUBLIC_` 접두사를 안 씁니다 — 그 접두사가 붙으면 Next.js가 "어차피 공개해도 되는 값"이라고 오해해서 브라우저 번들에 끼워 넣어버려서 마스터키가 전 세계에 노출되거든요. 셋째, **수명이 다름** — 본채는 사용자가 접속하는 동안 계속 살아있지만, 별채는 1회 실행 후 종료(M1.3에서 장기 실행으로 진화).

핵심 설계 원칙이 또 한 번 지켜졌습니다. **crash 금지**(env 없어도 `src/supabase.ts`가 throw 대신 null 리턴 + `console.warn`만), **Step 4의 경계 명확화**(supabase 파일은 만들되 `index.ts`에서 import 안 함 — Step 5에서 한 줄 추가만으로 ping 검증 가능하게 연결점만 비워둠), **dataService 추상 vs 워커 직접 클라이언트 분리**(워커는 `service_role`로 RLS 우회 + 배치 쓰기가 본업이므로, AI/web이 거치는 dataService 추상을 우회하는 게 Architecture §10 분리 원칙). code-reviewer가 발견한 W2(`main()`을 `async + .catch()`로 선반영)도 이번에 같이 적용해서, Step 5에서 `await supabase?.from(...)` 한 줄을 더하는 순간 unhandled rejection이 자동으로 graceful하게 잡힙니다.

이번 step에서 작은 파동은 **0건**. Step 3에서 ESLint v16 export 형태와 `.prettierrc` override 함정을 미리 겪어둔 덕분에, Step 4의 `typescript-eslint v8` flat config는 context7 공식 문서의 `eslint.configs.recommended` + `...tseslint.configs.recommended` 패턴을 그대로 적용해서 한 번에 통과했습니다. 단, esbuild 빌드 스크립트 경고(`pnpm approve-builds`)가 떴는데 이건 tsx가 esbuild의 WASM fallback으로 동작하기 때문에 무시해도 안전 — `pnpm -F @travis/worker dev` 결과가 즉시 정상 동작으로 증명됨.

## 🧭 주요 의사결정 (4건)

1. **TS 런타임 = `tsx` (Node.js 24 native TS 거부)** — Node.js 24의 `--experimental-strip-types`은 매력적이지만 context7 공식 문서가 명시: **`tsconfig.json`을 무시**하고 `enum`/`namespace` with runtime code/parameter properties/decorators가 모두 `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`. M1.3 어댑터에서 이런 문법 쓸 가능성 높음 → tsx 채택. 비용 devDep 1개, 이득 모든 TS 문법 + esbuild 속도 + Step 5에서 `tsx --env-file=.env`로 dotenv 의존성도 0개로 끝낼 수 있음.

2. **`src/supabase.ts`는 export만, `index.ts`는 import 안 함** — ROADMAP line 144~147이 Step 5에서 ping 추가를 명시. Step 4에서 ping까지 호출하면 (a) "env 없어도 graceful" 검증이 ping 실패 → 에러 핸들링 추가 → scope creep로 흐려짐, (b) Step 5의 명확한 작업이 사라짐. 그래서 "전기 콘센트는 매립하되 기계는 다음에 꽂는다" 패턴.

3. **`@travis/shared` 선제 배선 vs `@travis/data-service` 미포함** — 사용자 Q1 결정으로 shared는 포함(M1.2 매끄러움), data-service는 Architecture §10 분리 원칙으로 제외(워커는 `service_role` + RLS 우회 + 배치 쓰기가 본업이라 추상의 안전망 불필요). M1.3에서 워커도 dataService 경유로 통일할지는 deferred decision.

4. **W2(try/catch 가드) 즉시 채택** — code-reviewer가 "Step 5에서 `await` 추가 시 unhandled rejection 가능 → 지금 한 번 넣어두면 Step 5는 한 줄만 추가" 권장. Step 4 본질("crash 금지" 원칙 강화)에 직결되어 scope creep 아님으로 판정. ROADMAP 검증 조건("hello + exit 0")은 동일하게 통과 + Step 5 부담 ↓ + CLAUDE.md graceful 원칙 ↑ → 3중 이득.

## ⚠️ 다음 step에서 조심할 것

- **Step 5 (Supabase env 투입)**: 진입 직전 3가지를 동시에 챙겨야 합니다.
  - **(a) `.env` 로드 방식**: tsx는 `.env`를 자동 로드 안 함. **`tsx --env-file=.env src/index.ts`로 `dev` 스크립트 수정** 권장 (Node 20.6+/tsx 4.x 지원, 의존성 0개). 대안 dotenv 패키지보다 간결.
  - **(b) NodeNext 상대 import 확장자 룰**: `apps/worker/src/index.ts`에 추가될 한 줄은 **반드시** `import { supabase } from "./supabase.js";` (소스가 `.ts`여도 `.js`). VSCode auto-import가 `.ts` 또는 확장자 없이 생성할 수 있어 즉시 type-check 빨갛게 뜸 → 디버깅 가능. 패키지 import(`@supabase/supabase-js`, `@travis/shared`)는 확장자 불필요, 상대 import만.
  - **(c) Step 4에서 W2(`async + .catch()`)를 이미 선반영했으므로** Step 5는 정말로 "import 1줄 + ping 1줄"이면 끝. main 시그니처 변경 불필요.

- **M1.2 (4개 레지스트리)**: `packages/shared/src/index.ts`의 `SHARED_PLACEHOLDER` 제거 + 첫 레지스트리 export 추가. 워커는 이미 `@travis/shared` dep 배선되어 있어 `import {...} from "@travis/shared"` 즉시 동작. 추가 `pnpm add` 불필요.

- **M1.3 (첫 어댑터 + 로깅)**: code-reviewer S1·S5 트리거 — (a) `@types/node`를 v22→v24로 승격 검토, (b) `src/supabase.ts`를 `getSupabase()` 함수형으로 리팩토링(테스트 mock 대응), (c) `console.*` → pino/winston 마이그레이션, (d) `src/adapters/` 디렉토리 신설. 그리고 **W4(console.warn 모듈 시점)** 재검토 — Step 5에서 import 추가 후 환경에 따라 노이즈 될 수 있음.

- **M1.3 후반 또는 별도 위생 step**: code-reviewer W1 트리거 — `apps/worker/dist/tsconfig.tsbuildinfo` 빈 폴더 위생. `tsBuildInfoFile`을 `node_modules/.cache/`로 이동 또는 worker는 `incremental: false` 검토. `.gitignore`가 막아주므로 시급하지 않음.

- **M1.6 (Auth + 보안 감사)**: 워커의 service_role key가 클라이언트로 새지 않을 구조적 안전망(env prefix + .gitignore + Next.js 미경유)을 이번 step에서 확립함을 보안 감사 시 근거로 사용.
