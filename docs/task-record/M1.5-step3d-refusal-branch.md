## 3. 핵심 설계 포인트

### 3.1 왜 early return 위치가 `extractPayload` **이전** 인가

route.ts L276-293 의 refusal 분기는 반드시 `extractPayload()` 호출 전에 위치. 이유:

- `extractPayload()` 는 USE_TOOL_USE 모드에서 `toolUses[0]` 가 없으면 Error throw.
- refusal 응답은 tool_use 블록이 0 개이므로 extractPayload 가 "tool_use 블록 없음" Error 로 catch → `validation_exhausted` 오분류.
- 따라서 **검증 파이프라인의 맨 앞** 에서 stopReason 으로 먼저 가지치기 해야 정확히 분류.

이 위치 선택이 뒤집히면 Step 3d 자체가 무의미해지므로 주석으로 못박음 (route.ts L276-280).

### 3.2 `z.enum` + switch exhaustiveness 의 실전 효과

`OrchestrateFallbackReasonSchema` 에 `"refusal"` 을 추가하는 순간, `messageForReason()` switch(default 절 없음) 가 TypeScript `noImplicitReturns` 규칙에 걸려 **컴파일 에러로 누락을 강제**. 실제 구현 흐름:

1. 스키마에 enum 값 추가 → TypeScript 이 switch 미처리 감지 → 컴파일 에러
2. switch 에 case 추가 → 컴파일 통과

이 "enum 1 개 추가 시 모든 consumer 가 컴파일 에러로 변경 강제" 패턴이 향후 `pause_turn` 등 새 stop_reason 추가 시에도 자동 가드 역할.

### 3.3 haikuClient 의 조건문 의미 전환

**변경 전**: "empty 이면 throw" (empty=비정상)
**변경 후**: "empty 이고 그 이유가 refusal 이 아니면 throw" (empty=정상 사례도 존재)

도메인 지식(refusal 은 정상적인 empty) 을 코드에 직접 인코딩. 6 개월 후 자기 자신이 읽어도 헷갈리지 않도록 L246-252 주석에 이유 명시.
