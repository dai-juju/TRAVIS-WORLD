## 📖 비전공자 친화 설명

이 단계는 **메뉴판 4장의 빈 형식**을 만드는 핵심 작업입니다.

식당 비유로 설명하면: "요리명 / 재료 / 가격 / 사이즈" 같은 **칸의 구조**를 4장의 메뉴판에 인쇄한 것입니다. 아직 실제 요리(Binance, TickerCard 등)는 적혀있지 않지만, 이 형식만 있으면 나중에 아무 요리든 추가할 수 있습니다.

4장의 메뉴판:
1. **거래소 메뉴판**: "이름 / 지원 마켓(현물·선물) / API 주소 / 배치 지원 여부"
2. **데이터소스 메뉴판**: "이름 / 갱신 주기 / 필터 가능한 필드 목록" — 이 "필터 가능한 필드 목록"이 핵심. AI가 "거래량 상위 10개"라는 요청을 받으면 이 목록을 보고 `volume_24h > 0, 내림차순 정렬`이라는 필터를 만들 수 있음.
3. **컴포넌트 메뉴판**: "이름 / 지원 사이즈 / 갱신 모드(value: 숫자만 변경 / content: 목록 항목 동적 변경) / 필요한 데이터 형태"
4. **인터랙션 메뉴판**: "이름 / 타입(spawn: 새 카드 생성 등) / 받는 파라미터"

각 메뉴판에는 Zod(검수원)가 붙어서, 형식에 맞지 않는 항목은 등록이 거부됩니다.

## 🧭 주요 의사결정 (3건)

1. **Map 기반 단순 저장소 (class 기반 레지스트리 거부)**: 레지스트리는 모듈 수준 Map + 순수 함수로 구현. class로 감싸면 DI 설정이 필요하고 복잡도만 증가. 현재 요구사항에 Map + 함수가 적합.

2. **Zod 스키마에서 타입 추론 (interface 이중 선언 거부)**: `z.infer<typeof Schema>`로 타입을 추론하여 Zod 스키마와 TS 타입이 항상 동기화. interface를 따로 선언하면 불일치 위험.

3. **InteractionType에 drill_down/linked_selection 미리 선언 (spawn만 선언 거부)**: 타입 enum에는 미리 넣어두되 "M1에서는 spawn만 구현"이라는 원칙 유지. 나중에 enum 변경 없이 확��� 가능.
