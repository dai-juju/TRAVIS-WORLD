## 📖 비전공자 친화 설명

이번 Step 5는 TRAVIS 워커가 **"도매시장에 매초 장 보러 왕복하던 것"을 "도매시장에서 직통선으로 실시간 배달받는 것"으로 바꾼 작업**입니다.

Step 4까지는 REST API로 3초마다 "지금 BTC 얼마?" 물어보는 방식이었습니다. 이게 rate limit(시간당 질문 한도)을 계속 터뜨려서 IP ban 직전까지 갔습니다. Binance 공식 권고가 **"실시간 갱신엔 WebSocket 쓰세요 — ban 회피"**라서, 이 말 그대로 수신 경로를 바꿨습니다.

WS는 "프론트엔드 실시간 표시 전용"이 아닙니다. 워커(서버 내부)가 Binance로부터 데이터를 **질문-답변 방식(REST) 대신 구독-방송 방식(WS)**으로 받는 것. 받은 데이터는 여전히 Supabase에 같은 방식으로 upsert됩니다. **받는 방식만 바뀌고, 저장 경로는 불변**.

핵심 효과 4가지:
1. **IP ban 위험 완전 제거** — WS는 weight 카운터와 무관 (Binance 공식). SPOT rate limit 경고 "0건" 확인.
2. **실시간성 10~30배 향상** — BTCUSDT age가 REST 30초 → WS 1초로 단축.
3. **청산 이벤트 수집 최초 도입** — Step 4에는 없던 history_futures_liquidation 테이블 실제 INSERT 시작.
4. **`volume_chg_5m` 해석 B 전환 구조 완성** — Step 4에서 "근사" 상태였던 컬럼이 1m kline 기반 정확한 계산으로 자동 전환. M1.4 "(근사) 뱃지 제거" 조건 충족.

### E1 scope 경계 (사용자 확정, 2026-04-20)
**문제**: Binance는 전체 시장 kline 스트림(`!kline@arr`)을 제공하지 않음. 심볼별 개별 구독만 가능 (공식 문서 확인). 전 심볼 × 4 intervals = 17,196 streams → 최소 17 WS 연결 필요.

**E1 결정**: 사용자 "전 심볼 공평" 철학 엄수 + 스토리지 부담 회피 타협
- **1m kline**: 전 심볼 WS 구독 → `volumeKlineWindow` (in-memory) 에만 push → `volume_chg_5m 해석 B` 계산. DB 저장 **없음**.
- **5m/1h/1d kline + history_*_kline 저장**: **이번 step 제외** → M2 또는 M1.4 구현 중 실제 kline 필요성이 보이면 승격.
- WS 연결 수: 공통 3개(BinanceWsRelay) + kline chunk 6개(BinanceKlineRelay: SPOT 4 + USDM 1 + COINM 1) = **총 9개**. Binance "5분당 300 연결" 한도 대비 매우 여유.

## 📋 도메인 특이사항

### Binance WS 스트림 스펙 실증
| 스트림 | 마켓 | 포맷 | 용도 |
|---|---|---|---|
| `!miniTicker@arr` | 공통 | 배열 (거래 있는 심볼만) | ticker 24h 스냅샷 |
| `!markPrice@arr@1s` | USDM/COINM | 배열 (전 심볼) | mark/index/funding/nextFT |
| `!forceOrder@arr` | USDM/COINM | **단일 객체** (이벤트) | liquidation 이벤트 |
| `<symbol>@kline_1m` | 공통 | 단일 객체 (k.x로 봉 완성 구분) | 1m kline |

- miniTicker는 array 형태로 여러 심볼이 한 메시지로 옴 — 거래 있는 심볼만 포함됨 (거래 없는 심볼은 이전 값 유지)
- forceOrder는 청산 발생 시에만 단일 객체로 push — 배열 파싱 로직과 다름
- kline은 tick마다 업데이트 (k.x=false)되며 봉 완성 시 x=true — 미완성봉도 volumeKlineWindow에 replace 패턴으로 push

### COINM miniTicker quote_volume 필드 없음
- SPOT/USDM miniTicker는 `q` (quote_volume) 필드 제공
- **COINM은 `q` 없음** (BTC 담보 특성) → DB에 null 저장 정상
- M1.4 카드에서 COINM만 quote_volume 컬럼 숨김 처리가 맞음

### Mixed-batch 불변 실전 검증
- `markPriceWsHandler` 가 `interest_rate` 키를 row 객체에서 제외
- SDK가 columns union으로 SQL 생성 → interest_rate는 컬럼 리스트에서 제외 → 기존 REST 값 유지
- MEMORY `feedback_mixed_batch_invariant.md` 가 **실제 WS/REST 혼합 경로에서도 작동** 증명

### volume_chg_5m 해석 B 발동 조건
- `sampleIntervalMs=60_000` 에 의해 1분당 1 sample 저장
- **최소 10분 구동** 후 10개 sample 축적 → 해석 B 작동
- 그 전까지는 해석 A fallback — 부팅 후에도 연속성 유지
- 거래 없는 심볼은 1m kline 스트림이 push 없음 → 해석 A 계속 유지 (null 아닌 값)

## 🔧 Hot-patch (2026-04-20 후속 보강)

Step 5 본 작업 완료 후 1시간 steady-state smoke 준비 중 4건의 실측 이슈 발견 → 동일 세션 안에서 전부 해소.

### 발견 1 — SPOT kline WS HTTP 414 (URI Too Long)
- **증상**: `[BinanceKlineRelay] spot#0 error: Unexpected server response: 414` 무한 재연결 루프.
- **원인**: `CHUNK_SIZE=1,000` 일 때 Combined Stream URL 길이가 ~18KB → Binance(일반 HTTP 8KB 한계) 거부. 공식 문서의 "1 connection ≤ 1,024 streams" 는 **논리 한도만** 명시하고 URL 길이는 언급 없음.
- **수정**: `apps/worker/src/ws-relay/BinanceKlineRelay.ts` — `CHUNK_SIZE: 1_000 → 250` (URL ~4.5KB). SPOT 6 + USDM 3 + COINM 1 = **총 10 연결** 로 분할.
- **효과**: 재연결 루프 해소, 전 SPOT 심볼이 단일 smoke 안에서 connected.

### 발견 2 — `getSymbols` 가 SPOT 1,000 만 반환
- **증상**: 부팅 로그 `심볼 로드 완료: spot=1000 ...` — 이전 smoke 에서 3,562 이라 기재돼 있던 수치와 괴리.
- **원인**: Supabase/PostgREST 서버측 `db-max-rows=1,000` 설정이 `.limit(10_000)` 을 덮어씀. 서버캡은 client 쿼리 파라미터로 우회 불가.
- **수정**: `packages/data-service/src/SupabaseDataService.ts::getSymbols` — PAGE=1,000 pagination 루프 + `.order("exchange").order("market_type").order("symbol")` 정렬 명시. 이제 total 4,309 row 까지 안전 조회.
- **효과**: 모든 심볼 정확 조회 가능.

### 발견 3 — "SPOT 3,562" 기록이 실제로는 TRADING 1,408 + BREAK 2,151
- **증상**: 이번 smoke 에서 `spot=1408` 로 찍혔으나 "pagination 버그"로 오해할 뻔함.
- **확인**: Supabase MCP `SELECT market_type, status, count(*) FROM symbols WHERE exchange='binance' GROUP BY 1,2`:
  - SPOT: TRADING **1,408** / BREAK 2,151
  - USDM: TRADING **608** / SETTLING 102 / PENDING_TRADING 2
  - COINM: TRADING **30** / DELIVERING 8
- **결론**: "SPOT 3,562" 은 `symbols` 테이블 전체 rows 기준 오기재. 실제 구독 대상(TRADING) 은 1,408. BREAK 는 Binance 가 거래 일시 중단한 상태로 WS push 도 오지 않아 구독 의미 없음.
- **수정 (부수)**: 본 문서 / `docs/ROADMAP.md` / `docs/DB_SCHEMA.md` / `memory/project_m1_3_step5_ws_relay.md` 수치 정정.

### 발견 4 — `index.ts::loadAllSymbols` 의 COINM 호출만 `status` 필터 없음
- **증상**: COINM `openInterest/topLongShortAccount/taker` 각 8건 실패 로그 `Symbol is on delivering or delivered or pre-trading`.
- **원인**: COINM getSymbols 호출 시 "TRADING 표기 일관되지 않음" 가정으로 status 필터 생략 → DELIVERING 8개까지 포함됨. 실제로는 정상 일관 표기.
- **수정**: `apps/worker/src/index.ts::loadAllSymbols` COINM 호출에 `status="TRADING"` 추가 (주석도 현실 반영으로 업데이트).
- **효과**: COINM DELIVERING 8개는 WS kline 구독 대상에서 제외. (REST perSymbolTask 는 이미 `status="TRADING"` 호출하므로 별도 수정 불필요.)

### 발견 5 — 부팅 쿼리 hang (Supabase 간헐 장애 시)
- **증상**: Supabase 일시 Cloudflare 522 + connection timeout 발생 시 `loadAllSymbols` 의 `await dataService.getSymbols(...)` 가 무한 대기 → 워커가 "부팅..." 로그 이후 멈춤.
- **원인**: fetch 요청에 timeout 가드 없음. `Promise.all` 은 한 쿼리 실패 시 전체 reject (부분 성공 활용 불가).
- **수정**:
  - ➕ `apps/worker/src/utils/withTimeout.ts` — generic Promise 타임아웃 유틸 (timer leak 방지 포함).
  - ✏️ `apps/worker/src/index.ts::loadAllSymbols` — `Promise.allSettled` + `withTimeout(60_000)` 로 재작성. 한 마켓 timeout 나도 다른 마켓 진행 (graceful degradation). 실패 마켓은 빈 심볼 리스트 → `KlineRelay` 는 0 연결로 정상 작동.
- **효과**: Supabase 장애 중에도 부팅 차단 안 됨. 실패한 마켓의 WS kline 구독만 skip, 이후 poller 재시작 주기에서 복구.

### Hot-patch 파일 변경 요약
| 파일 | 변경 |
|---|---|
| `apps/worker/src/ws-relay/BinanceKlineRelay.ts` | CHUNK_SIZE 1,000→250 + URL 414 배경 주석 |
| `packages/data-service/src/SupabaseDataService.ts` | `getSymbols` pagination + `.order()` |
| `apps/worker/src/index.ts` | COINM `status="TRADING"` 추가 + `Promise.allSettled` + `withTimeout` |
| `apps/worker/src/utils/withTimeout.ts` | 신규 — generic Promise timeout 유틸 |

### 1시간 steady-state smoke 상태
- **미완료** — Supabase free tier 간헐 pause/wake 사이클 + Cloudflare 522 로 재현성 없어 연기.
- **대안 근거**: (1) Step 5 본 smoke 60초에서 fresh_2m 100% / 4도메인 공존 84.6% / liquidation 15건 실증, (2) 1시간 smoke 시도 중에도 warm-up 이후 steady-state 진입 관찰 (heap 67MB / window 정상 축적 / perSymbolTask 721s 완료 / WS 10 connections connected), (3) 기본 재연결/stale 감지/shutdown 로직은 단위 테스트 + 60초 smoke 에서 검증 완료.
- **Follow-up**: 아래 §Supabase Free Tier 한계 진단 참조. 1시간 smoke 는 M1.4 카드 구현 중 자연스러운 end-to-end 검증으로 대체 가능.

## 🏥 Supabase Free Tier 한계 진단 (1h smoke 차단 근본 원인)

1시간 smoke 를 막은 실제 원인이 "우리 코드 회귀" 가 아니라 **Supabase Free Tier 의 구조적 한계**임을 전문가 진단으로 확정.

### 관찰된 증상 (4종)
| 시점 | 증상 | 레이어 |
|---|---|---|
| A | Cloudflare **Error 522** HTML 반환 (`zvqvevwwtakjukdkdind.supabase.co` host error, Cloudflare Ray `9ef3efebe1b7d1ce`) | 인프라 (Cloudflare ↔ Supabase origin) |
| B | MCP `execute_sql` → `Connection terminated due to connection timeout` | PostgREST API |

### 근본 원인 (유력순)

**원인 1 — Supabase Free Tier compute sleep + cold-start** ⭐ 가장 유력
- Free tier 는 공식적으로 "7일 무활동 시 프로젝트 pause" 정책이지만, 실제로는 **짧은 idle 구간에서도 compute instance 수준의 sleep 발생**. shared compute 인프라의 비공식 동작.
- Cold-start 중 요청이 들어오면 → Cloudflare 가 origin wait → **수초 내 응답 없으면 522 반환**. 오늘 본 증상과 정확히 일치.
- 회복 후엔 warm 상태로 정상 응답 (B→D 전환 관찰).

**원인 2 — Free Tier compute 리소스 한계**
- Free tier 스펙: **0.5 vCPU / 500MB RAM / shared IO**.
- PostgREST direct connection 기본 한도 **~15개** (Supabase 내부 pool).
- 우리 워커 부하: WS 초당 upsert (ticker/markPrice/forceOrder × 3 마켓) + perSymbolTask REST + MCP 쿼리 → concurrent 요청이 순간 15개 초과 가능. 초과분은 queue → timeout → 502/522.

**원인 3 — Region latency (보조 요인)**
- Cloudflare Ray 에서 Seoul edge 확인 — 사용자 위치.
- Supabase 프로젝트 region 은 대개 `ap-northeast-1` 또는 `ap-southeast-1` (대시보드에서 확인 가능). 거리 기반 latency 가 부하 시 합산.

**배제된 원인**
- ❌ 코드 버그: hot-patch 이전에도 동일, 네트워크 레이어 에러라 특정 쿼리와 무관.
- ❌ 권한/RLS: service_role 키는 RLS 우회, 증상과 무관.
- ❌ 프로젝트 suspended: 대시보드 active 확인됨.
