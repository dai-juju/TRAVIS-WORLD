## 5. ★ forward-fill 방식 확정 (설계 lock-in)

- **증분 lookback = 봉(bar) 단위**(최근 1~2봉), 일 단위 아님. `executeHistoryBackfill` 재사용.
- **interval 그룹별 스케줄**(PollTask `intervalMs` = "execute 완료 후 휴식"): 단기봉(5m/15m/30m) ~10분 / 중기봉(1h/2h/4h/6h) ~1h / 장기봉(12h/1d) 1일 1~2회.
- **freshness = `getMaxRecordedAt(marketType, interval)` 정공** — row-count 임계는 증분 부적합 (Step 2 신규 dataService 메서드, `[8-25]`).
- **idempotent**: 자연키 onConflict + defaultToNull:false → 겹치는 lookback 안전.

## 6. ★★ Step 2 인계 부채 (code-reviewer S2/S3/S5 — Step 2 plan 필수 반영)

1. **(S2, 최중요) 증분 startMs 직접 주입** — `executeHistoryBackfill` 은 항상 `now - lookbackMs` 부터 돈다(backfill 전용). forward-fill 이 그대로 쓰면 **매 cycle 14일 전체 재수집**. Step 2 forwardFillTask 는 (a) DB 최신 `recorded_at` 조회 → (b) 그 시점~now 만 윈도잉. `ExecuteBackfillDeps` 에 `startMs` 주입 옵션 추가가 깔끔(코어의 lookback 자동계산은 backfill 전용으로 보존).
2. **(S3) COINM basis `"PERPETUAL"` 하드코딩** (`historyBackfillCore.ts:98 부근`) — COINM 은 contractType 체계 상이(`CURRENT_QUARTER` 등). Step 2 COINM 일반화 시 분기 필요. **marketType 별 별도 cycle 강제 — USDM+COINM 행 섞어 upsert 금지**(mixed-batch 불변, `feedback_mixed_batch_invariant`). `@crypto-domain-expert` OI=contract 단위 검증 동반(`[8-3]`).
3. **(S5) 부팅부 `loadUsdmSymbols` → `loadTradingSymbols(marketType)`** 일반화 — 코어는 이미 marketType 일반화(1-B)인데 collector 부팅부만 USDM 박제 비대칭.
