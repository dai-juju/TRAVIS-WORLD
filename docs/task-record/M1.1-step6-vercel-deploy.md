## 📖 비전공자 친화 설명

Step 1~5에서 집(모노레포)을 짓고, 전기(Supabase)를 연결했습니다. 하지만 이 집은 아직 "우리 컴퓨터"에서만 볼 수 있었죠. Step 6은 이 집을 **인터넷 세상에 공개하는 작업**입니다.

**Vercel**이라는 "웹사이트 호스팅 서비스"에 GitHub 저장소를 연결했습니다. 이제부터 코드를 GitHub에 push하면, Vercel이 자동으로 "새 코드 올라왔네!" 하고 빌드해서 `travis-web.vercel.app` 주소로 배포합니다. 마치 원고를 출판사에 넘기면 자동으로 인쇄·배포되는 시스템을 구축한 것과 같습니다.

배포 전에 한 가지 기술적 "포장" 작업이 필요했습니다. TRAVIS의 코드는 여러 패키지(폴더)로 나뉘어 있는데, 이 패키지들이 완성된 JavaScript가 아닌 **TypeScript 원본**을 그대로 제공합니다. Vercel 빌드러는 기본적으로 이런 원본을 처리하지 못하므로, `transpilePackages`라는 설정으로 "이 패키지들은 네가 직접 변환해"라고 알려줘야 했습니다. 이게 없었으면 빌드가 100% 실패했을 겁니다.

이 단계가 완료됨으로써 **M1.1 전체가 완료**되었습니다. TRAVIS의 기반 공사(땅 고르기 + 기둥 세우기 + 전기 연결 + 인터넷 공개)가 끝났고, M1.2부터는 이 기반 위에 실제 기능을 올리는 작업이 시작됩니다.

## 🧭 주요 의사결정 (3건)

1. **`transpilePackages` 추가 (빌드 스크립트 분리 거부)** — workspace 패키지에 별도 빌드 스텝(`tsc` → `dist/`)을 추가하는 대신, Next.js의 `transpilePackages`로 빌드 시 자동 트랜스파일하는 방식 선택. 이유: 패키지가 2개뿐이고, 별도 빌드 스텝은 개발 경험(DX)을 복잡하게 만듦. 패키지가 늘어나면 재평가 가능.

2. **빌드 설정 = Vercel 대시보드만 (vercel.json 거부)** — 설정이 3줄뿐이라 파일 관리 오버헤드 불필요. 빌드 실패 시 fallback으로 vercel.json 추가 가능. vercel.json을 쓰면 Root Directory 설정 방식이 달라져서 복잡도 증가.

3. **프로덕션 console.log 가드 = `NODE_ENV` 분기 (로그 완전 제거 거부)** — 개발 환경에서는 여전히 유용한 로그이므로 제거 대신 환경 분기 선택. 경고 로그(`console.warn`)는 모든 환경에서 유지 — env 누락은 프로덕션에서도 알아야 함.
