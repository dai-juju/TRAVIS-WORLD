## 📖 비전공자 친화 설명

Step 1에서 "TRAVIS 부지"를 정리했다면, Step 2는 그 부지 위에 **빈 방 두 개의 벽만 세운 것**입니다. 방 안에 가구는 아직 없고, 문패만 걸어뒀어요. 이 방들의 이름은 `@travis/shared`(공용 부품 창고)와 `@travis/data-service`(데이터베이스와 대화하는 통역사 방)입니다.

조금 풀면 이렇습니다. 앞으로 Step 3에서 `apps/web`(사용자가 보는 웹)을 만들 때, 웹은 `import { SupabaseDataService } from "@travis/data-service"` 같은 코드로 이 통역사 방에 손을 뻗을 거예요. 그런데 **그 방이 아예 존재하지 않으면 손을 뻗을 수 없죠**. 그래서 Step 2는 "방 자체를 먼저 짓기"입니다 — 방 안에 가구(메서드)는 M1.3에서, 4개 레지스트리 부품들은 M1.2에서 채울 예정. 지금은 정말 **빈 방 + 문패**만 있습니다.

특히 통역사 방의 핵심은 **`IDataService`라는 빈 계약서**입니다. CLAUDE.md의 "deferred decision(나중에 정하자)" 원칙에 따라, 이 계약서에는 도장 찍을 칸(메서드)이 한 칸도 없어요. **왜요?** 미래에 Supabase에서 TimescaleDB나 ClickHouse로 DB를 갈아탈 때 배관 전체를 뜯지 않으려면 이 계약서가 필요한데, **계약서의 구체 항목은 실제로 데이터를 부르는 사람이 생기는 M1.3 시점에 가장 정확하게 결정**되기 때문입니다. 지금 추측으로 메서드를 적으면 M1.3에서 99% 다시 갈아엎게 되거든요. 그래서 "양식 자리만" 만들고 끝냈습니다 — 이건 Architecture.md §10에 명시된 우리 프로젝트의 핵심 원칙(`dataService` abstraction layer = safety net)을 첫 코드 줄에서 지킨 것입니다.

이 단계에서 작은 파동이 한 번 있었어요. 처음에 만든 코드가 TypeScript에서 "필드를 만들었는데 안 읽어!"라고 에러를 냈는데, Plan에서는 "이 에러가 안 날 것이다"라고 잘못 예측했었습니다. code-reviewer 서브에이전트가 이 모순을 짚어줘서, **`@ts-expect-error`로 무성으로 막는 방법 대신 `void this.client;`라는 명시적 한 줄**(미래에 누가 봐도 "아 이건 임시 코드구나" 알아챌 수 있는)로 바꿨습니다. 작은 차이지만, "모르면 컴파일러 입을 막아"가 아니라 "아는 것만 명시적으로"의 문화를 첫 패키지부터 심어둔 셈입니다.

## 🧭 주요 의사결정

1. **Plan의 TS6133 진단이 틀렸음을 검증·교정**: 원 plan은 "noUnusedLocals는 함수 스코프 로컬만 체크"라며 `private readonly client` 필드를 그대로 두면 된다고 판단. 실제 구현 후 `pnpm type-check`에서 `error TS6133: 'client' is declared but its value is never read` 발생. → code-reviewer가 "`@ts-expect-error`는 self-cleaning이 영리하지만 무엇을 억제 중인지 모를 위험"을 지적. **`void this.client;` 명시적 no-op 읽기**로 교체. 생성자 끝의 `void` 한 줄은 컴파일러 지시어가 아니라 일반 코드라서 미래 개발자가 즉시 의도를 읽을 수 있고, M1.3에서 첫 메서드가 추가될 때 자연스럽게 제거 대상이 됨.

2. **`@supabase/ssr` 의존성 제외 → Step 3 `apps/web`으로 이월**: 원 plan에는 `packages/data-service/dependencies`에 `@supabase/ssr ^0.5` 포함이 명시돼 있었음. 그러나 `SupabaseDataService`는 `createClient(url, key)`만 호출(Node 호환 형태)하므로 ssr 패키지가 제공하는 `createBrowserClient`/`createServerClient`(Next.js `cookies()` 의존)를 쓰지 않음. 워커도 ssr이 필요 없음. 공유 패키지는 **runtime-agnostic** 유지하는 게 깨끗하다고 판단 → ssr은 cookie 컨텍스트가 필요한 `apps/web/lib/supabase.ts`(Step 3)에서만 import.

3. **`exports` + `types` 필드 패턴 채택, `main` 제거** + **`"type": "module"` 추가**: 원 plan은 `"main": "./src/index.ts"`만 명시. `tsconfig.base.json`이 `moduleResolution: "bundler"`를 쓰므로 Next.js Turbopack과 tsx 모두 `exports` 필드를 우선 참조. `main`은 `exports` 존재 시 무시되므로 제거. `"type": "module"`은 Step 4 `apps/worker`(tsx)가 `.ts` 파일을 ESM으로 인식하기 위해 필수. 추후 dist 빌드 전환 시 `exports`의 두 문자열만 `./dist/index.js` / `./dist/index.d.ts`로 교체하면 됨.

- **M1.2 첫 레지스트리 추가 시점**: `packages/shared/src/index.ts`의 `SHARED_PLACEHOLDER`는 `@deprecated` 태그가 붙어 있음. 첫 레지스트리(`exchangeRegistry` 등) 추가하면 즉시 삭제. IDE 취소선이 보이면 옳은 신호.
- **M1.2 동시 작업 권장**: `packages/shared/tsconfig.json`에 `"compilerOptions": { "lib": ["ES2022"] }` 오버라이드를 추가. 현재는 base의 `lib: ["ES2022", "DOM", "DOM.Iterable"]`을 상속하므로 shared 코드에 실수로 `window`/`document`가 들어가도 type-check 통과. 워커(Node.js)에서 런타임 폭발 위험. 주석에 명시는 했으나 타입 수준 강제는 M1.2에서 함께.
- **M1.3 SupabaseDataService 생성자 강화**: 현재는 `constructor(url, key)`가 빈 문자열/undefined 검증 없음. M1.3 진입 시 `if (!url || !key) throw new Error("...env 키 누락...")` 추가 권장 — CLAUDE.md "절대 crash 금지"는 graceful fail 메시지로 해결.
- **Step 3 (apps/web)**: 패키지 import 시 `import { SupabaseDataService, type IDataService } from "@travis/data-service"` 형태로 `type` 키워드 사용 필수 (`verbatimModuleSyntax: true` 강제). barrel(`index.ts`)이 `export type { IDataService }`로 정리돼 있어 import 측에서 `type` 키워드를 빼먹으면 TS1484 발생.
- **Step 3/4 어느 시점에 `exports` 필드 subpath 보강 가능성**: 일부 도구가 `package.json` 직접 읽으려 할 때 막힐 경우 `"./package.json": "./package.json"` 추가. 지금은 미리 안 넣고 실제 문제 발생 시 즉시 대응 (YAGNI).
- **별도 cleanup task 후보 (Step 2 책임 밖)**: 루트 `pnpm format:check`가 17개 pre-existing 파일에서 fail. `.claude/agents/` 등은 gitignored이지만 prettier가 무시하지 않음. `.prettierignore`에 `.claude/` `docs/future.md` 등 추가하거나 일괄 `prettier --write` 결정 필요. 현재는 CI gate가 아니므로 우선순위 낮음.
