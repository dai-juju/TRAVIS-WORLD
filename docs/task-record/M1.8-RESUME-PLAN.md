## 5. 사용자 결정 영역 영구 등재 (다음 응답에서 사용자 컨펌 필요)

### 5.1 D20 — 실 backfill 시점

> **권장**: (C) 마일스톤 종료 후 별도 사이클

**이유**:
- 본 마일스톤의 본질 = 현재 시점 카탈로그 완성 (사이트=DB 일치) + 표시 단위 정공
- 시계열 backfill 은 별개 가치 (M2 분석 카드 / heatmap / liquidation feed 등 의 기반)
- 본 마일스톤 종료 후 (commit ~19~21) 종단 게이트 통과 → M2 진입 전 별도 사이클 ("M1.8.5 history backfill" 또는 M2 Step 0 영역)
- 운영 분리 명확 (실 backfill ~2.28h 운영 비용 + Supabase 용량 ~2GB 증가 = 별도 의사결정)

### 5.2 D21 — Basis 포함 여부

> **권장**: (B) 6 metric (Basis 포함)

**이유**:
- 사용자 요구 #3 의 "선물 지표 7+ × 인터벌 9+" 안에 Basis 포함 (현재 시점은 §8.2a-2 의 fetchBasisBatch 로 채워짐)
- 시계열 영역도 동일 metric coverage 가 자연 정합
- 분량 증가 ~30% (27K → 33K REST, 20M → 25M row) — IP quota (2.28h → 2.97h) / Supabase 용량 (2GB → 2.5GB) 안에 안전
- canonical-metrics.md §2 가 이미 Basis 정의 완료 — 코드 차원 신규 fetcher 1개만 추가

### 5.3 D22 — schema interval 컬럼

> **권장**: (A) `interval VARCHAR(5)` 컬럼 ADD + PK 재구성

**이유**:
- (B) recorded_at implicit 은 충돌 가능 — 5m 봉 12:00 row 와 15m 봉 12:00 row 가 같은 PK 차지 불가
- (C) 9 테이블 분기 (`history_futures_indicator_5m`, ..., `_1d`) 는 Supabase 영역 폭증 + 쿼리 N-way UNION 복잡도
- (A) 가 표준 OLAP fact table 패턴 — 인덱스 추가 (`(symbol, interval, recorded_at)`) 로 쿼리 성능 확보

**필요 SQL** (8.3c 진입 시점):
```sql
-- 1) interval 컬럼 ADD
ALTER TABLE history_futures_indicator
  ADD COLUMN interval VARCHAR(5) NOT NULL DEFAULT '1d';

-- 2) PK 재구성 (기존 id PK 유지, UNIQUE 추가)
CREATE UNIQUE INDEX history_futures_indicator_natural_pk
  ON history_futures_indicator (exchange, market_type, symbol, interval, recorded_at);

-- 3) DEFAULT 제거 (마이그레이션 후)
ALTER TABLE history_futures_indicator
  ALTER COLUMN interval DROP DEFAULT;
```
