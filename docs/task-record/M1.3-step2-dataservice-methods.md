## 📖 비전공자 친화 설명

TRAVIS의 **"데이터 출입구 단일화"** 작업입니다.

비유: 지금까지는 주방(웹앱·워커)에서 식재료 창고(Supabase)에 누구나 직접 드나들 수 있었습니다. Step 2부터는 반드시 **조리보조(dataService)** 를 거쳐야만 창고에 들어가도록 규율을 만들었습니다.

조리보조는 네 가지 일을 합니다:
1. **DB 스키마 → TypeScript 타입 자동 동기화** — Supabase가 뱉어준 `database.generated.ts`를 진실 공급원으로 삼고, 사람이 쓰기 편한 짧은 이름(`NowFuturesTickerInsert` 등)으로 별칭만 얹음. DB가 바뀌면 이 생성 파일 재생성만으로 전체 코드가 자동 재검증.
2. **IDataService라는 계약서** — 어떤 데이터를 넣고 빼는지 인터페이스로 선언.
3. **SupabaseDataService라는 구현체** — 계약에 맞춘 실제 Supabase 호출. 나중에 TimescaleDB/ClickHouse로 갈아끼울 때 이 파일만 교체.
4. **절대 crash 금지** — 모든 메서드가 throw 대신 `Result<T>`(성공/실패 봉투)로 감싸서 반환.

**가장 까다로운 부분**: `upsertNowFuturesIndicatorPartial`. `now_futures_indicator` 한 줄에 펀딩/OI/롱숏/테이커 4개 소스의 값이 **서로 다른 폴링 주기**로 들어옵니다(펀딩 8h, OI 5m 등). 이걸 단순 upsert로 쏘면 나중에 온 호출이 먼저 값을 NULL로 덮어쓰는 참사가 생깁니다. Supabase의 `defaultToNull: false` 옵션을 써서 **객체에 없는 키는 SQL 컬럼 리스트에서 빠지게** 만들어 기존 값 유지를 보장.

이제 apps/web · apps/worker 양쪽에 싱글톤 인스턴스가 주입되어 있고, **런타임 파일에서 `.from()` 직접 호출 0건** (smoke script만 예외). 나중에 AI 오케스트레이터(M1.5)도 이 경로만 쓰게 됩니다.

### 작성된 메서드 13개 (M1.3 Step 2 범위)

**쓰기 (11개)**
- `upsertSymbols(rows)` — 심볼 마스터 upsert
- `upsertNowSpotTicker(rows)` / `upsertNowFuturesTicker(rows)` — _now ticker upsert
- `upsertNowFuturesIndicatorPartial(rows)` — partial UPDATE (핵심)
- `insertHistorySpotTicker(rows)` / `insertHistoryFuturesTicker(rows)` / `insertHistoryFuturesIndicator(rows)` — _history insert

- `insertLiquidation(rows)` — 청산 이벤트 insert

**읽기 (2개)**
- `getSymbols(filter)` — `{exchange?, marketType?, status?}` 필터 (limit 2000, 돌파 경고)
- `getNowSpotTicker(exchange, symbol)` — smoke/단일 조회용

M1.4 카드 소비자 전용 읽기(queryNowTickers, queryHistoryKlines 등)는 **해당 마일스톤에서 실제 소비 지점 기준으로 추가**(deferred decision 원칙).

## 🧭 주요 의사결정

1. **테이블별 전용 메서드** (세분화 전략): 제네릭 `upsert<T>(table, rows)` 대신 `upsertSymbols`, `upsertNowSpotTicker` 같이 테이블당 한 메서드. 메서드 수가 늘어나지만 TS 자동완성·실수 방지가 강해서 AI 오케스트레이터가 호출 시 더 안전. 파일 분할은 유지보수 필요해지면 그때.
2. **Supabase MCP 자동 생성 + 얇은 별칭 래퍼** (타입 생성): Zod 수동 정의·순수 TS interface 대신 자동 생성. DB 진실 공급원 유지 + 오타 방지. AI 출력 validation용 Zod는 M1.5에서 별도.
3. **Step 3~5 쓰기 + 최소 읽기 2개만** (Step 2 스코프): ROADMAP의 "인터페이스 먼저 정의 → 실 소비자 나올 때 확장" 원칙. M1.4 카드·M1.5 AI 메서드는 해당 마일스톤 진입 시 추가.
4. **클라이언트 DI** (자동 채택): dataService가 createClient 안 하고 외부에서 주입. web은 `@supabase/ssr`, worker는 service_role 옵션 이미 다르므로 중복 생성 방지 + 테스트 mock 주입 용이.
5. **Result<T> 패턴** (자동 채택): throw 금지. IExchangeAdapter의 FetchResult와 동일해 Step 3에서 어댑터 → dataService 체인이 자연스러움.
6. **partial UPDATE에 `defaultToNull: false`**: `.upsert(rows, { defaultToNull: false })`로 객체 키에 없는 컬럼은 SQL에서 빠지게. 두 가지 invariant 주석으로 박아둠: (1) 반드시 배열 시그니처로 호출, (2) 같은 배치 내 모든 row는 같은 key 집합.
