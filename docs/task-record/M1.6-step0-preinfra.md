## 📖 비전공자 친화 설명

**집짓기로 비유하면 "본 공사 시작 전에 현장 사무소를 설치하고 벽돌·시멘트·거푸집을 미리 배송받아 두는 단계"입니다.** 이번 Step 0 에서는 코드를 거의 건드리지 않습니다. 다음 3가지만 준비해 둡니다:

1. **현장 감리단 고용** — M1.6 부터 인증/RLS/보안 로그가 들어오므로, 이걸 전담으로 감독할 **`@security-auditor` 서브에이전트**를 새로 만들었습니다. 기존 `@code-reviewer` (일반 감리) 와는 역할을 명확히 분리해 — 전자는 보안만, 후자는 품질만 — 이중 감독 구조를 짜뒀습니다.
2. **Supabase 출입문 부품 주문** — Next.js 서버가 로그인 세션을 쿠키로 유지하도록 해주는 **`@supabase/ssr` 패키지**를 설치했습니다. 이걸 안 깔면 Step 1 에서 "로그인은 되는데 새로고침하면 풀리는" 현상이 나옵니다.
3. **로그인 폼 재료(shadcn) 배송** — 로그인 화면에 쓸 **`Form`·`Label` 컴포넌트**를 shadcn 에서 받아 `components/ui/` 에 넣었습니다. `Card`·`Button` 은 이미 있었습니다. Step 1 에서 UI 작업을 시작할 때 "아, 폼 컴포넌트가 없네" 하고 멈추는 일을 미리 없앴습니다.

**왜 이 작은 Step 이 중요한가**: CLAUDE.md "한 번에 하나의 작업" 원칙 때문입니다. Step 1 에서 "Auth UI 짜다가 중간에 `@supabase/ssr` 이 없네 → 설치 → 그런데 shadcn 도 없네 → 설치 → 컨텍스트 잃음" 흐름이 생기면 플랜이 깨집니다. Step 0 에서 미리 깔아두면 Step 1 은 **"UI 조립" 한 가지 일에만 집중** 할 수 있습니다. 요리로 치면 미즈앙플라스(mise en place) 단계.

## ⚠️ 다음 Step (Step 1) 에서 조심할 것

- **`@security-auditor` 활성화 시점**: 현재 session 은 에이전트 파일이 생긴 직후여서 **아직 description 인덱스에 반영되지 않음**. 다음 `/clear` 이후 새 session 부터 자동 위임 가능. Step 1 착수 시에는 아직 활용 못 함 → **Step 6 M1 완료 직전 종합 감사** 가 첫 실활용.
- **`@supabase/ssr` vs `@supabase/supabase-js`**: 둘 다 남아있습니다. SSR 패키지는 Next.js Server Component / middleware / route handler 에서 쿠키 기반 세션을 관리. supabase-js 는 service_role 클라이언트 / browser 쿼리에서 여전히 사용. Step 1 에서 **용도 혼선 주의** — 서버에서 `createBrowserClient` 쓰거나 클라이언트에서 `createServerClient` 쓰면 런타임 에러.
- **새 `form.tsx` 는 react-hook-form 을 transitively 요구**: 342 packages 중 `react-hook-form` 이 포함됐을 가능성 있음. Step 1 에서 로그인 폼 구현 시 `useForm` / `zodResolver` 패턴 사용 가능. `@hookform/resolvers` 가 없으면 별도 설치 필요할 수 있음 — Step 1 1b 착수 시 확인.
- **components.json 의 `style: "new-york"` 유지**: 기존 카드 디자인과 톤 통일. 로그인 폼은 별도 디자인 결정 없이 shadcn 기본 new-york 톤 그대로 사용.
