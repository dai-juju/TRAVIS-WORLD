## 📖 비전공자 친화 설명

이번 Step 2는 **"카드라는 개념 자체의 계약서를 만드는 단계"** 입니다.

Step 1에서 빈 도화지(캔버스)를 깔았다면, Step 2는 세 가지 뼈대를 만들었습니다:

1. **계약서 (AiCardConfigSchema)** — AI(M1.5)가 "이 카드 그려줘"라고 JSON을 뱉을 때 "양식에 맞게 썼는지" 검사하는 문서. 식당으로 치면 주방 입구 체크리스트. 양식 안 맞으면 조용히 튕김(crash 없음).
2. **카드 껍데기 (CardContainer)** — 모든 카드가 공통으로 쓰는 상자. 헤더(제목 + 삭제 X 버튼) + 리사이즈 손잡이 + 콘텐츠 슬롯. 이 상자 안에 Step 3~5에서 실제 카드(Ticker / CoinList / KlineChart)를 끼워 넣게 됩니다.
3. **데이터 수도꼭지 (useRealtimeRow / useRealtimeTable)** — 카드가 "BTCUSDT 지금 가격 줘" 또는 "지금 살아있는 모든 심볼 줘"라고 요청하면 Supabase Realtime에서 알아서 데이터를 끌어오는 훅(hook). 1,400+ 심볼이 초당 1,400번 업데이트돼도 UI가 뻑나지 않게 **500ms에 한 번씩만 몰아서 화면을 그리는** throttle 전략이 핵심.

### 비유로 이해하기
- AiCardConfigSchema = **레스토랑 주문서 양식**. 메뉴명/사이즈/수량 다 적혀야 주방이 받아줌.
- CardContainer = **접시**. 파스타든 샐러드든 일단 이 접시 위에 담김. 접시에는 "요리 이름 표시" + "반납 버튼"이 달려 있음.
- useRealtimeRow = **수도꼭지 1개 버전** (BTC 가격만 받음). useRealtimeTable = **급수탑** (모든 심볼을 한 번에 받되 500ms 단위로 컵에 따라줌).

### 왜 지금 단계가 중요한가
이 계약서(AiCardConfigSchema)가 **M1.5에서 AI↔코드 통신의 절반**이 됩니다. Step 3~5에서 실제 카드 3종을 짤 때 이 계약을 따라야 하고, M1.5에서 Claude 한테 "이 형식으로 JSON 뱉어"라고 주는 tool 정의의 기초. 여기서 허술하게 만들면 나중에 AI 환각 필드가 프론트까지 새어들어 UI가 깨집니다.

## 🧭 주요 의사결정 (5건)

### 결정 #1 — `.js` 확장자 일괄 제거 (packages/shared)
**배경**: `packages/shared/src/index.ts` 가 `./registries/index.js` / `./schemas/index.js` 스타일로 import. Step 1까지는 apps/web 이 shared를 실제 import 한 적이 없어(Step 1 canvasStore는 `@xyflow/react`만 사용) 잠복해 있던 문제. Step 2에서 CardContainer가 `@travis/shared`의 `AiCardConfigSchema` 를 처음 소비하자 Turbopack 이 `.js → .ts` 매핑 실패로 500 에러.

**결정**: shared 전역에서 `.js` 확장자를 제거하고 extensionless import 로 통일. Turbopack/vitest/tsc 모두 bundler moduleResolution 에서 자동 해석.

**부수 효과**: worker 의 `tsconfig.json` 이 `moduleResolution: "NodeNext"` 를 override 하고 있어 extensionless import 를 거부. 해당 override를 제거해 base의 `bundler` 상속. 런타임은 `tsx` 가 실행하므로 영향 없음.

**왜 이게 맞는가**: shared 는 `exports.default = "./src/index.ts"` 로 소스 직접 export. Node native ESM 에서 실행되지 않고 항상 bundler(Turbopack/tsx/vitest)를 통과하므로 `.js` 확장자는 무의미한 가식.

### 결정 #2 — `TravisNodeData = { config: AiCardConfig }` 단일 진입점
**배경**: Step 1 의 `TravisNodeData` 는 `{ componentId?, updateMode?, payload? }` 느슨한 플레이스홀더.

**결정**: Step 2 에서 `config` 한 필드로 통일. AI 가 출력할 `AiCardConfig` 전체가 그대로 노드 data 에 들어가며, CardContainer 가 `config.componentId` / `config.updateMode` 등을 꺼내 쓴다.

**잃은 것**: 자유 payload. 대신 Realtime 데이터는 카드 컴포넌트 내부 훅으로 구독하고 store 에 넣지 않는다(성능).

### 결정 #3 — `cardComponentRegistry`(프론트) ≠ `componentRegistry`(shared)
**배경**: shared 의 `componentRegistry` 는 AI 프롬프트로 직렬화되는 메타데이터(필드 설명, 지원 updateMode). React 컴포넌트 참조가 여기에 섞이면 shared 번들에 React 가 따라오는 오염.

**결정**: `apps/web/lib/cardComponentRegistry.ts` 를 별도 생성 — `componentId → React.ComponentType` 매핑 전용. 프론트 번들에만 존재.

**배선**: `registerCards.ts::ensureCardsRegistered()` 를 CanvasStoreProvider 의 useEffect 에서 1회 호출. side-effect 집중으로 tree-shaking 친화적.

### 결정 #4 — `useRealtimeTable` throttle: 내부 working Map + 500ms flush 복사
**배경**: 1,408 심볼 × 초당 1 update ≈ 1,400 ev/s. 매 이벤트 setState 면 React 프레임 드롭.

**결정** (backend-infra-specialist 위임):
- 이벤트 도착 → `mutRef.current` Map 에 즉시 반영(리렌더 없음)
- `createThrottler(500ms)` 가 flush 예약 → 새 Map 으로 얕은 복사하여 setState
- throttleMs=0 이면 즉시 flush(테스트용)

**대안 기각**: "Map 참조 유지 + version counter" 는 React 19 의 `react-hooks/refs` 룰 (렌더 중 ref 접근 금지) 과 충돌.

### 결정 #5 — React 19 `react-hooks/static-components` false positive 는 JSX 라인에서 disable
**배경**: `const CardComponent = getCardComponent(id); <CardComponent ... />` 패턴이 lint 에서 "render 중 컴포넌트 생성"으로 오판.

**결정**: `// eslint-disable-next-line` 을 JSX 사용처(`<CardComponent>`) 위에 붙이고, **왜 안전한가**를 모듈 상단 주석에 명시 — registry 는 module-level Map 에서 **등록된 참조를 조회**할 뿐 새 컴포넌트를 만들지 않음.

**왜 수정 불가능한가**: 규칙이 정적 분석 기반이라 Map.get() 결과의 참조 안정성을 추론할 수 없음. 커뮤니티에서도 동일 false positive 보고 다수.

## 📋 도메인 특이사항

### Next.js 16 Turbopack + workspace TS 소스
- Turbopack은 monorepo 내부 `.js` 확장자 ESM import 의 `.ts` 매핑이 불안정. workspace 에서 `transpilePackages` 를 쓰더라도 extensionless import 권장.
- `exports.default = "./src/index.ts"` 로 소스 직접 export 하는 shared 패키지는 이 제약을 따른다.

### Supabase Realtime postgres_changes 필터 제약
- filter 는 단일 컬럼만 지원 (예: `symbol=eq.BTCUSDT`).
- 복합 PK (exchange, market_type, symbol) 는 서버에 `symbol` 만 보내고 클라이언트 `match(row)` 콜백에서 추가 검증.
- `useRealtimeRow` 의 `match` / `initialFetch` / `pk` 콜백은 호출자가 반드시 `useCallback` 으로 안정화 — 참조 변경 시 재구독.

### React 19 + Zustand Provider 패턴
- `react-hooks/refs` 룰: 렌더 중 `ref.current` 접근 금지.
- Zustand 공식 `useRef(null) + null 체크` 패턴 대신 `useState lazy initializer` 사용(Step 1 결정, Step 2 유지).
- `useEffect` 에서만 ref 읽기 → throttle 구현의 mutRef 도 이 규칙 준수.

### Zod `.strict()` 와 AI 환각 차단
- AiCardConfigSchema 의 모든 중첩 객체가 `.strict()` — unknown key 거부.
- CardContainer 는 `safeParse` 로 감싸 crash 금지 원칙 준수. 검증 실패 시 빨간 테두리 fallback 카드 렌더(삭제 가능 유지).

옵션 A: `{symbol}·{도메인}` 자동 조합 (예: `"BTCUSDT · 24h 스팟"`)
옵션 B: AI 가 자유 텍스트로 생성 (예: `"BTC 현재가 스냅샷"`)

트레이더 관찰: 현재 dummy 의 `componentId #id` 노출은 디버그용으론 OK 지만, 실카드에서 포지션 트레이더에게 노이즈. Step 3 TickerCard 헤더 설계 전에 결정 필요.

#### Q2 — 카드 삭제 UX
옵션 A: **즉시 삭제 + Undo 토스트 3초** (crypto-trader 추천)
옵션 B: 확인 팝업 (클릭 → "삭제하시겠습니까?")
옵션 C: `Shift+Click` 가드 (단순 클릭은 효과 없음)

트레이더 관찰: 현재 즉시 삭제 방식은 실시간 변동 중 오클릭 위험. 스캘퍼는 팝업 싫어하고, 스윙/포지션은 오삭제 비용 큼 — 그래서 Undo 토스트가 세 페르소나 타협점.
