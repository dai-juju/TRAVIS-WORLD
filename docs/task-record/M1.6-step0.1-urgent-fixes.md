## 📖 비전공자 친화 설명

**식당으로 치면 "메뉴판 이름이 주방 이름과 달라서 주문이 엉뚱한 곳으로 가던 문제"를 바로잡은 수정입니다.** 손님(유저)이 "Top gainers 보여줘"라고 주문하면 웨이터(AI)가 메뉴판(registry)을 보고 주방(Supabase)에 "ticker_futures 접시 가져와"라고 전달하는데, 정작 주방에는 그런 이름의 접시가 없고 `now_futures_ticker`라는 다른 이름으로 보관되어 있었습니다. 그러니 주방이 "그런 접시 없는데요?" 하고 빈손으로 돌아오고, 손님은 "! realtime error" 라는 에러 메시지를 받게 된 거죠. 이번 수정은 **메뉴판의 이름을 주방의 실제 이름과 똑같이 통일** 해서 주문이 곧바로 실제 접시에 도달하도록 만들었습니다.

같은 세션에서 사용자가 테스트하다 두 번째 문제도 발견했습니다 — "BTCUSDT 가격 보여줘"라고 하면 카드 제목이 "Bitcoin vs Tether" 같은 **신문 헤드라인 스타일** 로 뜨는 현상. 이건 웨이터(AI) 에게 "editorial tone 허용" 이라고 가르친 문구와 예시 JSON 안에 박혀있던 "Bitcoin vs Tether" 라는 샘플이 **AI 학습 텍스트로 작용** 해 트레이더가 한눈에 "BTCUSDT"라고 보고 싶어하는 방식과 충돌한 겁니다. 3년차 바이낸스 트레이더는 화려한 수사가 아니라 티커 심볼을 스캔하므로, 가이드라인을 "clarity 우선"으로 바꾸고 예시 자체를 "BTCUSDT"로 교체했습니다.

이 수정은 **TRAVIS의 3개 데이터 경로 중 B (워커 → Supabase → Realtime → 프론트)** 가 막혀있던 걸 뚫은 것이고, **4개 레지스트리 원칙** 에서 "id = 프론트-AI 계약"이 실제 테이블명과 일치하도록 임시 정렬한 작업입니다. 정식 구조 결정(id를 추상 계약으로 유지하고 별도 `tableName` 필드로 분리할지)은 M1.6 Step 4에서 @zod-schema-architect 자문으로 다시 판단합니다.

## 🧭 주요 의사결정

1. **대안 A (id = 테이블명) 임시 채택** ← 대안 B (id 추상 유지 + `tableName` 필드 분리) 는 M1.6 Step 4 자문 대상이므로 선점 회피. 지금 대안 A 를 고른 이유는 (a) 수정 범위가 최소 (6곳 edit) 이고, (b) `TickerCard`/`CoinListCard` 의 기존 타입 (`NowTickerTable`) 이 이미 테이블명을 기대하므로 프론트 코드 0줄 수정으로 해결되며, (c) M1.6 Step 4 에서 대안 B 로 승격 시 되돌리기 쉬움. 구조적 결정은 deferred.

2. **8개 datasource 전체 리네임 거부 → 2개만** ← 초안은 전체 8개 를 정합성 위해 통일 제안. 기각 이유: 나머지 6개 (premium_index / open_interest / long_short_ratio / taker_long_short / symbols_meta / liquidation) 는 **현재 프론트 사용처 0건** — 건드리면 YAGNI 위반 + 불필요한 diff blast radius. 이들은 Step 4 에서 enum 승격 시 일괄 처리하면 한 번에 끝남.

3. **카드 제목: 예시 JSON 직접 교체 + 가이드라인 양쪽 수정** ← 가이드라인 문구만 바꾸는 옵션도 있었음. 기각 이유: Anthropic 공식 프롬프트 엔지니어링 가이드상 multishot example 이 guideline 텍스트보다 **더 강하게 AI 행동을 지배**. "editorial tone allowed" 만 지우고 예시에 `"Bitcoin vs Tether"` 를 남기면 AI 가 예시를 따라 계속 편집 톤을 생성. 양쪽을 동시에 조정해야 근본 차단.
