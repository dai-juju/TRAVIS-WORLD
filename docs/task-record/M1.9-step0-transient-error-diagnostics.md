## 2. 핵심 설계 결정 (2건)

### 결정 1 — 분류 책임 위치: haikuClient 가 status 추출, route 가 분류 (status 숫자가 인터페이스)
- `@anthropic-ai/sdk` 가 **value import 되는 곳은 `haikuClient.ts` 뿐** (route 는 `import type`). → SDK instanceof 결합을 haikuClient 에 가두고, route 는 status 숫자만 본다.
- `AnthropicTransportError` 에 `readonly status?: number` 3번째 생성자 인자 추가. catch 에서 `err instanceof Anthropic.APIError ? err.status : undefined` 추출.
- **실측 검증** (`node -e`, 2026-06-02): `Anthropic.APIError` 는 default export 에 붙은 함수(값), `.status` 가 인스턴스에 설정됨(402→402), `instanceof` 작동. **402(Payment Required)는 전용 클래스가 없어 base `APIError(status=402)` 로만 잡히므로 instanceof 가 아닌 status-숫자 기반 분류가 정공.**

### 결정 2 — 신규 enum 의 retryable 정책: 둘 다 `retryable: false` (현행 transient 와 동일)
- 셋 다 **이 핸들러 안에서 즉시 재호출 안 함** (Step 2b 는 transient 재시도 미도입, Zod self-correction 만 재시도).
- ⚠️ "재시도 원리적 무의미"는 아님 — 429 는 rate-limit window 후 backoff 재시도 가치 있음. 그 backoff 재시도는 M2+ rate-limit 큐 영역(`[4-28]`/`[8-10]`). route.ts 주석에 명시 (code-reviewer W1).

## 4. 핵심 발견 (영구 교훈)

1. **계획서 ≠ 코드 실제** — M2-plan §Step 1.5 는 "`log_chat.fallback_reason` CHECK 제약 갱신(`[3-29]` 동시 회수)"를 적었으나, 실사 결과 **CHECK 제약은 애초에 없음** (순수 `VARCHAR(40)`). 새 enum 2개는 DB 변경 없이 INSERT. → `[3-29]`("CHECK 추가 *여부*")는 미결정으로 잔존, 본 작업 무관. 실사 안 했으면 없는 제약을 고치려 헛걸음.
2. **동작 의존 코드 전 1줄 실증** — `instanceof Anthropic.APIError`/`.status` 를 코드에 넣기 전 `node -e` 로 SDK 실측. default vs named export 혼동·402 base-class 흡수를 사전 확인.
3. **enum N분할 시 동반 축 표류** (code-reviewer memory note) — 라벨(fallbackReason)은 쪼갰는데 `retryable` 동반 축은 일괄값 유지 → 의미 충돌 잠복. `feedback_fallback_reason_enum_drift` 확장판. M1.6 Step 4(validation_exhausted 2분할)·본 Step(transient 3분할) 동일 패턴.
