## 📖 비전공자 친화 설명

이번 Step 4는 TRAVIS 워커를 **"한 번 실행하고 끝나는 스모크 스크립트"에서 "계속 살아서 뛰는 심장"으로 승격**시킨 작업입니다.

Step 3까지는 마치 "주방장이 한 번 장보기 실습"을 한 수준이었습니다. 장을 보고 재료(시세·지표)를 창고(Supabase)에 넣고 끝. Step 4부터는 **"24시간 자동 운영되는 주방"** 이 됐습니다.

주방에 빗대어 핵심 부품 4가지:

1. **RollingWindow (심볼별 가격 기록장)** — BTC, ETH, SOL 각 심볼마다 "최근 25시간치 가격·거래량"을 서랍에 쌓아둡니다. 서랍 크기는 1,500개 한정 (1분 1개 샘플 × 25시간). 새 값이 들어올 때 1분 미만이면 맨 뒷 장부를 **덮어쓰기**, 1분이 지나야 새 장부로 **추가**. 이렇게 해야 3초 주기로 push해도 서랍이 터지지 않고 "1분 1샘플" 약속이 지켜집니다.

2. **preCompute (변화율 계산기)** — 현재 가격과 5분 전·15분 전·1시간 전·4시간 전 가격을 꺼내 비교해서 "몇 % 변했나?"를 계산. 순수 함수라 입력이 같으면 결과도 같아 단위 테스트가 깔끔. 과거 값이 부족하면 해당 변화율 컬럼만 null — DB가 이걸 허용하도록 설계되어 있어 문제 없음.

3. **TierPoller (타이머 관리자)** — 3개 작업(ticker/premium/perSymbol)을 각자 다른 주기로 자동 반복 실행. 작업이 실패해도 워커 전체가 죽지 않도록 내부에서 에러를 잡고, `Ctrl+C` 눌리면 "진행 중 작업 끝날 때까지 기다린 뒤" 깔끔하게 종료.

4. **3개 Task**:
   - **tickerTask (3초 주기)** — Binance Spot/USDM/COINM 3개 마켓의 24hr ticker를 동시에 한 번씩 가져오면 **4,299개 심볼 전체**가 한 방에. RollingWindow에 현재값 push **전에** preCompute로 변화율 계산, 계산 후 push. (순서가 중요 — 뒤집으면 자기 자신과 비교해서 변화율이 0%로 찍힘).
   - **premiumTask (30초 주기)** — 선물의 펀딩레이트·마크가격·예상정산가 등 6개 컬럼을 부분 UPDATE.
   - **perSymbolTask (~341초 실질 주기)** — Binance가 배치를 안 주는 지표 3종(OI 미결제약정, LSR 롱숏비율, Taker 매수/매도)을 심볼당 50ms 간격으로 순회. 한 바퀴 도는 데 실측 331초 + 10초 휴식 = 약 5분 40초 주기.

**데이터 흐름**: Binance API → 어댑터 → normalize → RollingWindow과거조회 → preCompute(변화율) → window에 현재값 push → 원시+가공 merge → Supabase `now_*` upsert.

**왜 "mixed-batch 금지"가 중요한가**: `now_futures_indicator` 테이블에는 펀딩, OI, LSR, Taker 4개 도메인 컬럼이 한 줄에 모여있습니다. "OI만 채운 row"와 "LSR만 채운 row"를 **같은 배치**로 upsert하면 Supabase SDK가 두 row의 키를 합쳐 SQL 컬럼 리스트를 만들고, 없는 컬럼은 NULL로 덮어씀 → **기존 값 손실**. 그래서 도메인별로 완전히 독립된 배치로 upsert해야 합니다 (Step 2 W2 hazard의 근거).

**사용자 철학 "모든 코인 공평"**: Tier 차등(BTC 빠르게, 알트 느리게) 없이 전 심볼 동일 주기. Binance rate limit과 타협한 결과가 "직선 순회 ~341초". 알트 3~4선 코인도 BTC와 같은 주기로 업데이트됨.

**현실적 타협 2가지**:
- `volume_chg_5m`은 Step 4에서 **근사**(24h 누적 거래량 차분, 해석 A). Step 5 WebSocket 연결되면 **진짜 5분 거래량 비교**(해석 B)로 자동 전환. 컬럼명은 유지, 데이터만 정확해짐.
- kline 폴링은 **통째로 Step 5로 이관**. per-symbol 제약 때문에 4,000 심볼 kline을 짧은 주기로 못 돌림. WebSocket의 `!kline@arr` 스트림이 훨씬 효율.

### perSymbolTask 실측 주기 발견 + 대응
- **예상 200초, 실측 331초** — backoff 포함. intervalMs=200_000 이었을 경우 "다음 tick 예약 = execute 완료 후 200초 = 실질 주기 531초" (9분)가 되어 사용자의 "최대한 짧게" 철학 위반.
- **대응**: intervalMs를 10_000 (10초)로 조정 + TierPoller 주석에 "intervalMs는 execute 완료 후 최소 휴식" 의미 명시. 실질 주기 ~341초(5분 40초) 달성.
- **Warning 반영 후 재구조화**: USDM/COINM 라인 병렬 + 심볼 캐시 TTL 1시간 → 실측 331초가 더 줄 가능성 (다음 smoke에서 확인).

## 🩺 사후 실측 검증 (2026-04-20 추가)

### 발견 #1 — `updated_at` 자동 갱신 누락 (**CRITICAL**)
- **증상**: 워커가 upsert를 정상 수행하는데도 `updated_at` 컬럼이 24시간 전 값에 고정. Supabase Realtime 구독자와 M1.4 카드 "몇 초 전 업데이트" 뱃지가 모두 거짓 신호가 될 위험.
- **원인**: 마이그레이션 `20260418000002_create_now_tables.sql` 의 `updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()` 는 PostgreSQL 규약상 **INSERT 시에만** 적용. upsert의 ON CONFLICT UPDATE branch에서는 기존 값이 그대로 유지됨.
- **조치**: 신규 마이그레이션 `supabase/migrations/20260420000001_add_updated_at_triggers.sql` 작성 + Supabase MCP `apply_migration` 으로 적용. `set_updated_at_now()` 함수 + 3개 `now_*` 테이블에 BEFORE UPDATE 트리거.
- **검증**: 3분 구동 후 verify → spot 3,562 / USDM 707 / COINM 30 모두 **30초 이내 갱신 100%**. 트리거 정상.

### 발견 #2 — `verifyStep4.ts` PostgREST max-rows 1000 cap (**HIGH**)
- **증상**: [4] spot 집계가 "총 1000, price_chg_5m 0%"로 보여 한때 사전계산 컬럼이 전부 빈 것으로 오판. 실제로는 3,562개 중 2,950개(82.8%) 채워진 상태.
- **원인**: Supabase PostgREST는 기본 `max-rows=1000` cap으로 `.select()` 결과를 서버에서 1000행으로 잘라서 반환. 순서 지정 없이 1000 가져오면 특정 심볼 range만 포함.
- **조치**: `verifyStep4.ts` 의 [4][5][6] 집계를 **client-side filter + length**에서 **server-side `{ count: "exact", head: true }` + `Promise.all` 6개 count 쿼리**로 재작성.
- **검증**: "총 3,562 / 100% 갱신 / 82.8% 사전계산" 정확 수치 출력.
