## 📖 비전공자 친화 — 무엇을 왜 하는가

### 비유 — "내 컴퓨터 → 24시간 데이터센터"

**현재 상태**: 사용자 Windows 11 컴퓨터에서 worker (데이터 일꾼) 가 돌아갑니다 — Binance 실시간 시세를 Supabase DB 에 매초 적재. 하지만:

1. **컴퓨터 끄면 DB 멈춤** — 이미 본 사고: 사용자가 Wi-Fi 끊고 컴퓨터 끄자 worker 정지 → DB 40시간 stale → 사용자가 카드 갱신 안 됨 발견.
2. **Windows 환경 특수 사고** — USDM `fstream.binance.com` 만 selective stuck (메시지 0건). SPOT/COINM 같은 클래스로 정상. backend-infra-specialist 진단 결과 "Windows + 사용자 ISP + ws library + 큰 페이로드 콤보" 강한 의심. M1.6 Step 4 hotfix B (mini 6필드 + REST 1분 폴링) 로 USDM 1분 stale 까지 후퇴 보강.

**Hetzner 이전 후 자연 해결 가능성**:
- **Linux TCP stack** 이 Windows 와 다름 — payload-size selective failure 회피 가능성 매우 높음
- **데이터센터 IP** 가 사용자 ISP 와 다름 — fstream selective stuck 자연 해소 가능성
- **24/7 가동** — 컴퓨터 종료 의존성 0

### 베타 배포 전이지만 지금 이전하는 이유

사용자가 베타 배포 자체는 늦게 진행하지만, **개발 중 사용자 검증이 USDM 1분 stale + fstream stuck 으로 자꾸 노이즈** 발생. M1.6 Step 5 (CI RLS + orchestrateOnce 단위 테스트) + M1.6 Step 6 (E2E + M1 완료 선언) 검증 자체가 worker 데이터 stale 영향 받음. **안정된 환경에서 Step 5/6 진행 = 검증 신뢰도 ↑**.

#### 🚨 24h 갭 사고 — monitor.sh `203/EXEC` (2026-05-02 발견 + 즉시 복구)

**사고 요약**: 사용자가 24h 후 dump 파일 검토 시점에 **로그가 1개만 존재** 발견 (`/var/log/travis-monitor/2026-04-29-18.log` 만, 4개 기대 vs 1개 실제). 진단 결과 `travis-monitor.timer` 는 정상 firing 됐으나 `travis-monitor.service` 가 매번 `status=203/EXEC` 로 즉시 fail. 24h 자동 baseline 누적이 **정확히 0건** 발생.

**원인 확정 (단 1줄로)**:
```
ssh ... "ls -la /opt/travis/apps/worker/scripts/monitor.sh"
→ -rw-rw-r-- 1 travis travis 12988 Apr 29 19:09 monitor.sh    ⭐ x 비트 없음
```

`apps/worker/scripts/monitor.sh` 의 git mode 가 `100644` 이라 Hetzner `git pull` 후에도 +x 비트 없음 → systemd `execve(2)` 가 EXEC 단계에서 fail. **첫 1회 (18:42) 만 성공한 이유**: 사용자가 `bash monitor.sh` 형태로 직접 호출 (interpreter 직접 호출은 +x 불필요). 그 후 timer 자동 firing 은 항상 EXEC 단계라 절대 못 넘김.

**근본 원인 (Windows 환경 함정)**: Windows 의 `git config core.fileMode = false` (기본값) 가 NTFS 의 항상-+x 보고를 회피하느라 mode 변경 추적을 끔 → 사용자 PC ls 는 `-rwxr-xr-x` 으로 보이지만 git index 는 `100644`. `git update-index --chmod=+x` 로 mode bit 만 명시 변경하면 회피.

**즉시 복구 (2026-05-02 00:05:28 UTC)**:
```powershell
ssh ... "chmod +x /opt/travis/apps/worker/scripts/monitor.sh && systemctl reset-failed travis-monitor.service && systemctl start travis-monitor.service"
ssh ... "sleep 5 && systemctl status travis-monitor.service --no-pager -l"
# → Active: inactive (dead) since ... code=exited, status=0/SUCCESS ✅
ssh ... "ls -la /var/log/travis-monitor/"
# → 2026-04-29-18.log + 2026-05-02-00.log (4761 B, 첫 baseline 의 약 2배)
```

**부분 영구화 (commit 동시 진행)**: `git update-index --chmod=+x apps/worker/scripts/monitor.sh apps/worker/scripts/monitor-install.sh` — 두 파일 git mode 100755 변경 (SHA hash 동일 = 내용 미변경 검증). 다음 Hetzner `git pull` 부터 +x 자동 보존.

## ⚠️ 다음 작업에서 조심할 것

- **Wi-Fi/네트워크 끊김**: 사용자 PowerShell 에서 `scp` 또는 `ssh` 작업 중 Wi-Fi 끊기면 부분 전송 발생. `scp` 후 `ls -la` 로 파일 크기 검증.
- **`.gitignore` 가드**: `worker.env` / `.env.production` 등이 git tracked 되지 않도록 `.gitignore` 사전 확인. Substep 0.3 직전 `git ls-files | grep -E '\.env'` 0건 검증.
- **Hetzner Backup vs Snapshot 차이**: Backup 은 자동 (7일 7개) — 본 Step 채택. Snapshot 은 수동 (보관 무제한, €0.011/GB/월) — 큰 변경 직전 추가 안전망용 권장.
- **`fstream.binance.com` selective stuck 재발 시**: Hetzner 에서도 재발하면 Binance API key 또는 ASN 기반 차단 가능성. 별도 진단 — backend-infra-specialist 자문 + crypto-domain-expert 자문 동시.
- **베타 배포 시점 alignment**: 사용자가 베타 배포할 때 Vercel `apps/web` 의 Supabase URL 변경은 **불필요** — Hetzner worker 도 같은 Supabase 인스턴스 쓰므로 자동 일치. 단 Hetzner worker 의 `BINANCE_API_KEY` 가 사용자 베타 배포 시점에 갱신 필요할 수 있음 (M1.7 Step 1 allowlist 와 무관).
- **Windows 에서 추가하는 모든 `.sh` 파일은 git mode 100755 검증 필수** (2026-05-02 신설): Windows 의 `git config core.fileMode = false` (기본값) 때문에 `git add scripts/foo.sh` 시 mode 가 `100644` 으로 commit → Linux systemd `execve(2)` 가 `status=203/EXEC` 로 즉사 (monitor.sh 사고 = 첫 발현). 신규 `.sh` 추가 시 `git ls-files -s <path>` 가 `100755` 인지 검증 + 아니면 `git update-index --chmod=+x` 적용. M1.7 Step 1+ 운영 스크립트 다수 예정이라 `.gitattributes` + PR 체크리스트 영구 정책으로 회수 ([3.5-9]).

```bash
chmod +x bootstrap.sh
./bootstrap.sh
```

`bootstrap.sh` 가 자동 처리할 작업:
- `apt update && apt upgrade -y` (시스템 최신화)
- `apt install -y ufw fail2ban unattended-upgrades` (방화벽 + brute-force 방어 + 자동 보안 패치)
- `ufw default deny incoming + allow 22/tcp + ufw enable` (외부 incoming 22번만 허용)
- non-root user `travis` 생성 + sudoers 등록 + `~/.ssh/authorized_keys` 복사
- `systemctl enable --now fail2ban` (sshd jail 자동 적용)
