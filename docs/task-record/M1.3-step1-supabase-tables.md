## 📖 비전공자 친화 설명

TRAVIS의 Supabase(데이터 창고)에 **11개의 선반(테이블)**을 설치한 단계입니다.

비유하면: 대형 마트를 새로 여는데, 상품을 진열하기 전에 "이 칸은 현물 시세", "이 칸은 선물 펀딩레이트", "이 칸은 과거 차트 데이터" 같이 선반을 배치하는 작업입니다. 아직 선반은 비어 있지만, Step 2~4에서 Binance 데이터가 채워집니다.

핵심 설계 원칙: 모든 선반에 **"어느 거래소", "어떤 마켓(현물/선물)", "어떤 심볼"** 3개 칸이 공통으로 있어서, 나중에 OKX/Bitget을 추가해도 **새 선반을 만들 필요 없이 기존 선반에 행(줄)만 추가**하면 됩니다. 이것이 TRAVIS의 확장성 원칙 — "오케스트레이터 코드 변경 없이 확장" — 의 DB 버전입니다.

또한 `_now`(지금 현재 시세) 테이블 3개에는 **Supabase Realtime**을 활성화했습니다. 이것은 "데이터가 바뀌면 프론트엔드에 자동으로 알려주는 기능"으로, M1.4에서 카드가 실시간으로 갱신되는 데 핵심적인 배관입니다 (경로 B).

- code-reviewer 리뷰 후 보완: `symbols`에 `tick_size`, `step_size`, `min_notional` 컬럼 추가, 주석 개선

## 🧭 주요 의사결정 (3건)

1. **데이터 종류별 테이블 + exchange 컬럼 (거래소별 테이블 분리 거부)**: 거래소 4개 × 마켓 3개 × 데이터 10종이면 120개 테이블이 되는 문제. `exchange` + `market_type` 컬럼으로 구분하면 11개로 충분하고, 새 거래소 추가 시 행만 추가. ROADMAP 확장 루프의 OKX 예시("테이블 추가 불필요")와 일치.

2. **USDM과 COINM을 같은 `now_futures_ticker`에 통합**: USDM은 `quote_volume`이 있고 COINM은 `base_volume`이 있어서 스키마가 약간 다르지만, 나머지 90%가 동일. `market_type` 컬럼으로 구분하고 해당 없는 컬럼은 NULL 허용. 별도 테이블보다 AI 쿼리가 간단.

3. **open_time/close_time을 BIGINT(epoch ms)로 저장**: Binance API가 밀리초 타임스탬프를 반환. TIMESTAMPTZ로 변환하면 1ms 미만 정밀도 손실 위험. 원본 보존 우선. dataService에서 필요 시 변환.

## ⚠️ 다음 step에서 조심할 것

- **Step 2(dataService)에서**: `now_futures_indicator`의 각 데이터 소스(펀딩, OI, 롱숏비율)가 **자기 컬럼만 UPDATE**해야 함. 전체 행 upsert 시 다른 소스의 값이 NULL로 덮어씌워질 위험.
- **Step 3(BinanceAdapter)에서**: `symbols` 테이블의 `tick_size`, `step_size`, `min_notional`은 exchangeInfo의 `filters` 배열에서 추출해야 함 (PRICE_FILTER.tickSize, LOT_SIZE.stepSize, MIN_NOTIONAL/NOTIONAL.notional).
- **Step 4(폴링)에서**: history 테이블은 무한 축적 구조. 파티셔닝/다운샘플링 없이 수백만 행이 쌓이면 조회 느려질 수 있음 — 확장 루프에서 해결 예정이나, 폴링 빈도를 과도하게 높이지 않도록 주의.
- **Step 5(WS)에서**: `!forceOrder@arr` 청산 이벤트는 `history_futures_liquidation`에 저장해야 함 (now 테이블 없음, 이벤트 직접 INSERT).
- **보완 마이그레이션**: `20260418000004_alter_symbols_add_trading_filters.sql`을 Supabase Dashboard에서 실행해야 함.
