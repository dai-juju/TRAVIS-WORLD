## 📖 비전공자 친화 설명

이번 Step 3은 **TRAVIS가 처음으로 실 데이터로 자기 DB를 채우기 시작한 순간**입니다.

Step 2까지는 레스토랑으로 치면 메뉴판(레지스트리)과 주방 식기(빈 Supabase 테이블)만 준비한 상태. 이번 Step에서 **Binance 시장에서 실제 시세·지표를 퍼와서 우리 DB에 덮어쓰는 "장보기 담당자(Adapter)"를 3명 고용**한 셈입니다 — 현물(Spot), USDT 마진 선물(USDM), 코인 마진 선물(COINM) 각 한 명씩.

담당자 3명은 **공통 장바구니 규칙**(`client.ts`)을 공유합니다:
- Binance가 "너무 자주 물어본다"고 화내면(429/418) Retry-After 존중 후 재시도
- 서버가 뻗으면(5xx) 1·2·4초 exponential backoff 3회
- per-symbol 엔드포인트(OI·롱숏비율·Taker)는 50ms 간격으로 하나씩 순회 (rate limit 보호)
- 모든 결과는 Result<T>로 감싸 throw 안 함 — 어떤 심볼이 실패해도 전체 수집이 멈추지 않음

가져온 원재료는 `normalize.ts`가 "우리 주방 규격"(Supabase 테이블 컬럼)에 맞게 썰어줍니다. Binance가 문자열로 준 가격("50000.00")을 숫자로, 없는 필드는 null로, camelCase(`lastPrice`)를 snake_case(`last_price`)로 변환.

**특히 중요한 설계**: Binance의 선물 지표(펀딩레이트·미결제약정·롱숏비율·Taker비율)는 **각각 다른 엔드포인트**에서 옵니다. 폴링 주기도 다르고요. 이걸 한 배치로 합쳐 upsert하면 Step 2에서 이미 실증한 "다른 도메인 컬럼이 NULL로 덮어써지는 hazard"가 터집니다. 그래서 **각 도메인별로 별도 배치 메서드**(`fetchOpenInterestBatch`, `fetchTopLongShortAccountBatch`, `fetchTakerLongShortBatch` 등)를 만들고, 각자 반환한 배치를 호출자가 따로따로 `upsertNowFuturesIndicatorPartial`에 쏩니다.

smoke 스크립트(`smokeBinance.ts`)가 실제 Binance API + 실제 Supabase를 상대로 돌아 **4,309개 심볼 + 4,299개 ticker + 765개 indicator 행을 1분 내에 upsert**했고, BTCUSDT 한 행에 premium·OI·LSR·Taker 4개 도메인이 **하나도 NULL로 안 덮이고 공존**하는 것을 DB에서 직접 확인했습니다. partial update 설계가 실제 라이브 데이터에서도 작동한다는 최종 증거.

마지막으로 사용자 결정 3건도 문서에 반영됐습니다:
1. **Hetzner 배포 연기** → ROADMAP Step 6 완전 삭제, §L.3 Launch Readiness로 이동. M1은 로컬 워커로 엔드투엔드 증명.
2. **per-symbol 순회 허용** → Binance API가 일부 지표를 per-symbol로만 제공하므로 예외 인정.
3. **volume_chg_5m 의미 = "24h rolling diff"** → Step 4 구현 시 주석에 명시 예정.

### Step 4 (폴링 + 사전계산) 진입 시
- **volume_chg_5m 의미 주석 박기**: "24h rolling 변화율, 실제 5분 거래량 아님" — normalize 또는 compute 레이어에 명시

- **메모리 롤링 윈도우**: `_history` 조회 없이 메모리에서 사전계산. 심볼 수 × 최근 N개 = 수백 MB 예상. 8GB RAM에서 관찰 필요
- **Hetzner 테이크: 아직 안 함** — 로컬 30분 무중단 검증으로 충분 (완료 기준 조정됨)
