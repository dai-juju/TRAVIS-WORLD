### 비유 — 식당의 3종 장부

1. **`log_chat`** = "유저가 AI 에게 무엇을 묻고 무엇을 받았는가" (1 query = 1 row, 13 컬럼). 트레이더가 "show me top gainers" 라고 입력하면 1 row INSERT — query_text / ai_response / 비용(input/output_tokens) / 지연(latency_ms) / 모델(model_id) / 성공여부(status) / 재시도횟수(attempt_number) 등이 한 줄로.
2. **`log_behavior`** = "유저가 화면에서 무엇을 만지작거렸는가" (event_type 자유 문자열 + payload JSONB). Step 3 에서 본격 채움.
3. **`log_validation_failure` 확장** = "AI 가 잘못된 JSON 을 뱉어 Zod 가 거절한 사례" (5 컬럼 추가 — user_id / attempt_number / model_id / system_prompt_version / user_query_hash).

### 자물쇠 (RLS) 의 정확한 역할

**RLS (Row-Level Security)** 는 Postgres 가 매 SELECT 쿼리에 자동으로 `WHERE user_id = <현재 로그인 user>` 조건을 추가하는 기능. 코드에서 까먹어도 DB 가 강제. M1.4 의 사고 ("RLS 켰지만 policy 0개 = 아무도 못 봄") 가 이 기능의 실측 증명.

이번 Step 2 의 RLS 패턴:
- **SELECT policy 1개** (각 테이블당): `auth.uid() = user_id` → 본인 row 만 조회
- **INSERT/UPDATE/DELETE policy 0개** → service_role (master key) 만 INSERT 가능. 클라이언트가 위변조 불가.
- **NULL user_id 자동 차단**: `auth.uid() = NULL` 은 항상 false → 익명화된 row 는 본인도 못 봄 (의도). admin (M1.7) 만 별도 policy 로 봄.

### "1 query = 1 row" 옵션 B 채택 (재시도 합산)

AI 가 1차 실패 → self-correction 재시도 → 2차에서 성공/실패 시나리오에서 2가지 옵션 검토:
- **옵션 A** (호출당 1 row): 비용 정확, rate limit 왜곡 (1 query 가 2 카운트)
- **옵션 B** (query 당 1 row): rate limit 정확, 비용은 합산 필드로 보존 ✅

M1.7 의 rate limit 의도가 "유저의 의도된 query 횟수 제한" 이므로 옵션 B 채택. 재시도는 시스템 내부 구현 디테일이지 유저 행위가 아님. attempt_number=2 + input/output_tokens 합산으로 비용 정확성 보존.

### `ON DELETE SET NULL` 의 우아함

사용자 의견 반영 (CASCADE → SET NULL). 유저가 탈퇴해도 row 자체는 보존, user_id 만 NULL. 이유:
- **회계 trail 보존**: "지난 3월 Anthropic 청구서 $84 가 누구 query 였나?" 추적 가능 (탈퇴자 포함)
- **Cohort/Retention 분석**: 탈퇴자 row 가 사라지면 잔존율 분모 왜곡
- **Fraud 탐지**: 탈퇴 후 재가입 abuse 패턴 발견 가능
- **GDPR 양립**: "잊혀질 권리" 명시 요청 시 admin tool 의 query_text 마스킹 절차로 대응 (`[3-23]`)

## 🧭 주요 의사결정

### 1. **`ON DELETE SET NULL` 채택** (CASCADE 기본 권장 → 사용자 의견 반영)

- **기각된 옵션 (CASCADE)**: GDPR "잊혀질 권리" 자동 충족이지만 비즈니스 분석 / 회계 trail / fraud 탐지 데이터 영구 손실.
- **채택 옵션 (SET NULL)**: row 자체 보존 + user_id 만 NULL → admin 만 (M1.7) 봄. RLS `auth.uid() = NULL` 자동 차단으로 일반 유저는 못 봄. GDPR 명시 삭제 요청은 admin tool 의 query_text 마스킹 절차 (`[3-23]`).
- **연결된 결정**: user_id `NOT NULL` → `NULL 허용` 으로 변경 (의미: NULL = 탈뢰자).

### 2. **이메일 비정규화 안 함** (UUID 만 저장)

- **채택**: log_chat 에 user_id (UUID) 만, 이메일은 `auth.users` JOIN 으로 조회.
- **이유**: PII 격리 강화 (log_chat leak 만으로 누군지 모름) + DRY (이메일 한 곳 진실) + 이메일 변경 자동 반영.
- **단점 수용**: admin dashboard 매번 JOIN 필요 (성능 미미).

### 3. **log_chat 풀세트 13 컬럼** (M1.7 dashboard 일괄 대비)

- model_id / input_tokens / output_tokens / latency_ms / attempt_number / system_prompt_version / user_query_hash 미리 추가.
- **이유**: M1.7 admin dashboard ("오늘 Haiku 호출수 / 예상 비용 / 실패율 / 평균 응답시간") 가 이 데이터에 직접 의존. 지금 안 넣으면 M1.7 ALTER 1회 추가 → migration 비용 + schema drift 위험.

### 4. **`log_behavior` 자유 문자열 `event_type`** (enum 박제 X)

- 후보 enum (`card_added` / `card_drag` / `card_resize` / `card_delete` / `canvas_clear` / `chat_submit`) 미리 박지 않음.
- **이유**: Step 3 hook 인스트루멘트 시 실제 가치 있는 이벤트 자연 발견. 미사용 enum 박제 = dead spec (CLAUDE.md YAGNI 위반).
- Step 3 마지막에 관찰된 이벤트로 enum CHECK 제약 추가.

### 5. **"1 query = 1 row" 옵션 B** (재시도 attempt 합산)

- **기각된 옵션 A** (호출당 1 row): 비용 정확, rate limit 왜곡.
- **채택 옵션 B**: input/output_tokens 합산 + attempt_number 분리. rate limit 의도 ("유저의 의도된 query 횟수 제한") 와 일치.
- 재시도는 시스템 내부 구현 — 유저 행위 카운트와 분리.

### 6. **service_role 전용 INSERT** (RLS policy 0개)

- **채택**: SELECT policy 1개 + INSERT/UPDATE/DELETE policy 0개 → anon/authenticated 자동 차단, service_role 만 RLS bypass 로 INSERT.
- **이유**: 클라이언트가 직접 INSERT 가능하면 status="success" 위조 → rate limit 우회 가능. server-side 만 진실 INSERT.

### 7. **system_prompt_version 채우는 방법** (env fallback 체인)

- `process.env.VERCEL_GIT_COMMIT_SHA ?? process.env.GIT_COMMIT_SHA ?? "dev"` — Vercel 자동 주입 변수 우선, local dev 는 "dev" placeholder.
- **이유**: 운영 단계에서 "프롬프트 vX 이후 실패율 변동" 회귀 분석의 anchor key. 사용자가 따로 할 일 없음 (Vercel 배포 시 자동).

### 8. **`user_query_hash` Step 2 컬럼만 + Step 3 채움**

- 컬럼은 추가, 실제 sha256 채우는 코드는 Step 3 logChat hook 작업 시 (Web Crypto API `crypto.subtle.digest('SHA-256', ...)`).
- **이유**: PII 격리하면서 동일 query 클러스터 분석 가능 (admin 이 query_text 못 봐도 hash 비교).

### 9. **Supabase Dashboard 직접 RUN** (MCP read-only mode 우회)

- Supabase MCP `apply_migration` 이 read-only 모드로 차단 → 사용자가 Dashboard SQL Editor 에 SQL 직접 붙여넣기 + Run.
- **이유**: destructive DDL 의 production 보호 boundary. AI 자동 적용 차단이 정확히 작동. M1.7 admin migration 도 동일 경로 권장.

### 10. **`logChat.ts` 와 `logValidationFailure.ts` 분리 유지** (factory 추출 보류)

- 90% 중복이지만 현재는 책임 분리 + mocking 의존성 명확.
- Step 3 에서 `logBehavior.ts` 추가 시 3 파일 동일 boilerplate → factory 추출 임계점 (`[3-27]` 이월).
